## 1. 对设计的结论

采用 **外部应用管理其对象及协作界面、Bingdi Bots 提供组织 Bot 原生能力与治理、Chronotope 提供耐久执行** 的分工。Bot 可内化业务知识/经验/技能，自主创建任务和调度业务工作。研究支持固定模型下优化 harness、检索配置和程序性技能的可行性，但不证明长期运行或反思自动带来可靠改进。

本轮调整重点是：

1. **协作先准入**：以强单 Agent 为基线，按任务、相同总预算决定是否启用专家或 peer；共享会话不默认全广播。
2. **记忆按行动验收**：事实 QA、多会话依赖任务、来源更新/删除、多用户 CRUD 分开测；完成和履约需要真实状态证据。
3. **经验分层且可撤下**：episode/fact/skill/obligation 分开；来源失效先阻断新使用，再异步修复派生产物。
4. **技能两道检查**：写入准入和使用时适用性/来源复验；授权正确也不代表程序性经验正确。
5. **优化与发布分权**：可诊断 development、有限查询 selection regression、独立 promotion audit 分开；自偏好只筛候选。
6. **有界改进**：最小变更、复杂度与全成本预算、最终组合 digest 重评；可信外层不进入首版自修改面。

Bots 拥有 Bot 原生知识、任务/计划/调度、工作承诺及其验收契约，也管理人格、策略和改进批准；存储可复用 Chronotope。外部应用决定它自己的会议、工单、订单、合同等对象状态、业务规则和权限。Bot 的“报告已生成/提醒已发出”可以独立验收，不自动等于“工单已关闭/合同已履行”；复制外部白黑名单或拒绝决议到 SOP 不能产生额外权限。

## 3. 设计增量与权威边界

### 3.1 从默认协作改为按任务准入

外部应用的一个会话可以有多个组织 Bot，每个 Bot 内部也可派发 children；**存在多个参与者，不意味着每条消息都应触发所有人推理**。Bots 管理 Bot 的 session/loop 参与方式和执行拓扑，使用外部 conversation/object 引用；业务触发资格、成员权限和源会话真相来自外部应用。Chronotope 执行有效治理及外部授权范围内的 fan-out、claim、异步任务和预算约束，Bots 不另建聊天协作应用。

准入对照至少包含强单 Agent、当前 Supervisor+children，以及确有需求的候选专家/peer。固定任务模型、工具权限、输入和**全团队总预算**，统计父子全部调用、等待和通信成本。收益不明确或关键回归发生时保留现行/单 Agent；不得通过额外隐藏预算证明协作“更好”。这是一项待验证策略，不是对所有任务禁止协作。[F12, F15]

### 3.2 从大摘要改为分层证据与有版本的事实

Bots 分层保存 episode、内化的业务知识/经验/技能、BotTask/Plan/Schedule 和 Bot 自身承接的工作责任。它们是 Bot 的知识与工作资产，可以存于 Bots 或 Chronotope，不限于外部引用/缓存，也不要求外部应用先有对应记录。外部对象另以 ExternalWorkRef 关联，保持各自 ID、状态和验收权威。Episode 引用实际 run/operation/provider receipt；不可变记录或 hash 不证明原陈述真实。[F07, F10, F11]

BotKnowledge 可保存有证据的断言、归纳和方法，记录 `source_refs/revision/observed_at/valid_time/confidence/applicability/supersedes` 并由 Bots 管理自身版本。来源系统中的字段仍以该系统为准；Bot 可形成不同假设或新经验，但须标明推断及支持，不据此直接改写外部对象。普通知识积累按已授权写入处理；改变行为的 skill/SOP/memory 方法才走候选晋升，不把每条记忆都当软件发布。

记忆评测覆盖知识召回/更新、多 session 依赖执行、来源失效和读取隔离。Bots 根据原生任务契约检验研究/报告/提醒是否完成，涉及外部对象的目标再采用其 API/验收证据。`run.completed`、BotTask 完成、发送接纳/送达和外部业务履约分别记录，不能互相推导。[F07, F13]

### 3.3 来源失效先设屏障，再修复

每份摘要、embedding、skill、prompt、harness patch、候选及评测诊断保存可追溯派生清单，字段含义以[职责边界 §4.2](./Chronotope与Bingdi-Bots职责边界.md#42-derivationmanifest-与-coverage)为准；这不是已实现的 API：

```text
DerivationManifest {
  artifact_ref, artifact_revision, artifact_digest,
  source_refs_and_revisions, predecessor_artifact_refs,
  producer_run_ref, bot_release_ref, policy_revision,
  authority_decision_refs, allowed_scope_refs,
  lineage_coverage, capture_boundary, known_gaps
}
```

`lineage_coverage` 表示声明捕获边界内的依赖覆盖程度，不能由模型自报 complete 后当作证明。来源当前 revision/epoch 另按权威记录检查；记录已读取来源和实际派生引用、扫描历史未知制品、保守隔离不确定范围都需要实现/验收。[F09]

外部应用提供有权来源纠正/删除/撤销信号，Bots 对自己的运行记忆和治理制品提交失效；各 owner 按事务/outbox 传播。Chronotope 的通用读/检索/派发机制与接入合同指定的实际 sender 均核验当前来源/授权状态。屏障确认后才可声称指定范围新操作已被阻断，跨服务未确认时保持 pending。后续异步重建、验证 successors，未验证制品维持隔离；外部源无失效接口时披露覆盖限制，不能推定已同步。失效修复不能等 canary，也不能因 release rollback 复活旧来源。

派生清单记录“内容受什么影响”，授权 grant 决定“谁能做什么”；二者不能互相替代。已经送入模型上下文或已经派发的操作不能靠删索引抹除；必要时中断/隔离对应运行，阻断后续输出并对账在途效果。本文不承诺完整机器遗忘、零泄露或撤回已经发送的消息。[F09, F14]

### 3.4 SkillCandidate 需准入与复用两道检查

技能至少记录不可变 digest、来源 lineage、适用任务/环境、前置条件、工具需求、禁用情形、反例、fallback 和评测引用。私有经历提炼的技能继续受原来源范围约束，扩大 audience 须单独授权。[F04, F05]

- **准入**：Bots 检查程序内容、反例、质量及 no-skill 对照；Chronotope 验证受信批准、制品身份并隔离执行。候选不能自行写入正式可用库。
- **复用**：Bots 检查当前任务/工具版本和技能适用条件；所有读取、工具、输出仍经过当前 grant/来源/受众门。授权失效或技能撤下时，缓存命中不得绕过检查。

ACL 只能限制访问，不能证明一个有权读取的技能是好程序。换 session 也不能清除已发布技能的影响。某技能被撤下时应定位后代候选和缓存并阻断新复用；仅回退当前 release 指针不够。[F05]

### 3.5 三类评测角色，隔离候选与发布权

| 数据角色 | 允许反馈 | 查询与用途 |
|---|---|---|
| Development | 可看逐题失败、轨迹及诊断 | 生成提案、失败聚类与调试；不能再声称独立盲测 |
| Selection regression | 预先限定的指标与诊断范围 | 有限自适应候选比较，持久记录访问/暴露；参与反复选择的分数不能冒充全新测试 |
| Promotion audit | 独立 runner 控制，受限汇总 verdict | owner 预设查询预算、样本及轮换规则；首个 PoC 采用新鲜批次一次性审计，曝光或耗尽后退出独立角色 |

Bot 治理与原生能力评测的集合、指标/阈值及晋升批准归 Bots 的受信服务。原生任务有自己的验收器；涉及外部系统对象终态或业务约束时采用该系统/权威服务的验证合同，不能用 Bot 自评覆盖。Chronotope 提供隔离 job、配额/访问执行和报告存证。审计规则提前固定，候选不能通过新 proposal/run 重置查询额度；普通记忆写入或已授权创建任务/闹钟不逐条经过这套发布审计。[F02, F03, F08]

GEPA 式结构化反思与 RHO 式自偏好可以作为两个可替换候选生成/预筛选器。自偏好、LLM judge、局部 QA 与“分数不退化”不能替代隐私、授权、重复副作用和承诺连续性的独立阻断项。[F03, F06, F11]

`EvalResult` 继续绑定 **最终** base/candidate digest、模型/参数、输入/记忆水位、评测版本/角色、预算与 scope。多个单独通过的补丁合并后必须评测合并 digest；不能拼接旧报告。Bots 的批准与 Chronotope 的 RuntimeReleaseBinding CAS 维持既有单一权威，不新增第二个 active 指针。

### 3.6 固定可信外层，小步修改内层

首版把“一簇失败→一个有界候选→独立评价”作为起点。除了任务/评测费用，也记录反思调用、候选重试、存储、工具和多 Agent 通信总成本，限制改动文件/配置域、依赖和运行时兼容面；具体阈值由试点事前确定。[F01, F02, F06]

候选可改 Bot 的检索/上下文配置、受控技能及 loop/SOP 执行方法，harness 代码先产补丁，由可信工程流程发布。SOP 引用外部规则/决议服务，不复制客户或成员白黑名单作为本地权威；外部拒绝不能经换账号/换 Bot/换 attempt 绕过。授权、审计、预算硬限制、发布权、外部业务/承诺合同和独立验证器不随候选自改。

反复 trial 的随机波动可能产生假改进。关键候选使用配对任务、预定重复/种子与不确定性判据；收益不足以区分时保留基线。AIDE² 的单次长运行提供可行性信号，尚不足以把“不断重写自身优化器”设为 MVP 成功条件。[F01]

## 4. 方案取舍

| 方案 | 优点 | 代价/风险 | 本期决定 |
|---|---|---|---|
| 固定策略，不做自改 | 归因清楚、验证面小，作为稳定对照 | 难以自动适应长期失败 | 保留为每轮基线及 fallback |
| 受限 retrieval/context 配置搜索 | 改动空间小，易隔离和回滚；EvolveMem 有直接参考 | QA 过拟合，配置组合也可能使长期行动退化 | **首个自动候选面**，必须通过四轨与领域反例 |
| 程序性 skill 演化 | 可复用工作方法，修改局部且可审查 | 有害程序可跨 session 持久传播 | **有限采用**，准入+复用检查、来源隔离、no-skill 对照 |
| GEPA/RHO 式 harness 优化 | 复用失败轨迹，允许结构化诊断/低成本预筛 | 偏好误判、重复试探评测、环境不可重置 | **离线比较**；真实不可逆动作不作为 replay |
| 全量在线自改代码/优化器 | 潜在搜索空间大 | 评测噪声、复杂度、发布兼容及治理面膨胀 | **后置**；本期只生成补丁，不追求自治递归加速 |
| 多 Agent 全广播/共享全记忆 | 原型直观、信息立即扩散 | 成本、污染、泄露和交接失败随之扩散 | **不作默认**；定向参与、私态隔离、按任务准入 |
| LLM 自判 public / fulfilled / 可发布 | 实现便捷 | 分类/自述不等于权威，错误会固化 | **不作权威**；只产生建议，受信服务依合同决议 |

上述研究没有提出替换 Restate 的充分证据。继续采用 PG inbox/outbox、有限 activation、异步 child 和持久 wait/signal；MCP/A2A 保持接口角色。是否引入新消息系统仍由可测瓶颈决定，不能因新论文增加第二套恢复 owner。

## 5. 期 8 的验证增量

此处是后续能力参考，**未执行且不作为当前 G1 前置**。先按期 8 G0/G1 跑通真实知识/提醒闭环，再选择对应 fixture；下表旧阶段编号只表示能力关联，不恢复 A–F 全量实施范围。

| 阶段 | 对照与产物 | 必须能反驳的假成功 | Owner / 期 8 落点 |
|---|---|---|---|
| T1 · 任务与协作基线 | 固定模型/输入/全团队预算；强单 Agent、Supervisor+child 与候选拓扑；保留完整成本与失败轨迹 | 增加 agent/隐藏调用就宣称协作有效；父采纳错误 child 自报完成 | Bots C；infra B5 提供任务/attempt/operation 证据 |
| T2 · 跨 session 记忆 | 内化业务知识、原生研究/报告任务、两个外部接入与来源 revision | QA 提高却执行失败；知识压缩丢失原生待办/承诺；本地推断覆盖外部对象 | Bots D1/D2 原生 verifier；外部对象 oracle；infra B2 |
| T3 · 失效与传播 | 外部受限源→摘要→skill→候选的完整链及故意缺边链 | 源失效仍复用缓存；不完整 provenance 却报零暴露；rollback 复活来源 | 源应用决议；Bots 自有派生失效；infra/实际 sender 屏障 |
| T4 · 小步非模型优化 | no-skill/当前版/候选；业务经验提炼的一个 skill/SOP 修改 | 自评分提升算发布；改原生任务既定验收或外部规则；有害技能跨 session 传播 | Bots D5 与原生 verifier；必要外部 oracle；infra 隔离 job/制品 |
| T5 · 发布与故障回归 | 独立审计、查询耗尽/样本披露、合并 digest 重评、CAS 冲突、回滚和迟到 run | 新 proposal 重置审计额度；A 报告发布 B；用 rollback 撤销事实/效果/义务 | Bots 批准；infra B6 生效；现有 G-B/G-D 联合验收 |
| T6 · 原生闹钟与主动工作 | 从会议信息生成 BotReminder/Schedule；独立待办、持久等待、重启及当前受众检查 | 必须先建外部日历事件才可提醒；重启重复发送；本地取消误删会议；报告生成冒充会议/工单完成 | Bots D2/E 原生调度策略；Chronotope wait/claim/receipt；外部应用仅保留会议权威 |

质量提升阈值、样本量、重复次数、允许回归与成本上限应在 trial 前确定；对授权、来源范围、重复效果和权威合同违反设独立拒绝项，不能用平均效用抵消。记录通过、失败、跳过和覆盖边界，不能把设计文档状态更新为性能已验证。

故障验收仍须验证 inbox/唤醒缺口、旧 generation/task attempt/auth epoch、未知发送效果和跨服务撤权确认。研究论文没有证明我们的 CAS、游标或 outbox 正确，引用不能代替本地 PoC。
