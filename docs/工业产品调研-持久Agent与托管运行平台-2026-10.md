> 本文补充[前沿研究](./前沿调研-持久Agent与非模型自改进-2026-10.md)与[运行时/协议横评](./调研-多Agent持久协作方案横评.md)。对 Chronotope / Bingdi Bots 的建议仍为**待实施设计**，不能与厂商公开功能混为交付状态。

## 1. 定位：需要同时比较三个层次

| 层次 | 本轮产品 | 与本项目的对应关系 |
|---|---|---|
| 面向人的长期 Agent 产品 | Claude Tag、dots、Grok Bot / Team Bots、Muse、Cue | 参考主体持续性、原生记忆/任务/调度、接入与隔离机制；个人所有权和聊天 UI 不照搬为 **Bots** 的产品定位 |
| 托管 Agent 运行平台 | Claude Managed Agents、OpenAI Agents API | 主要对照 **Chronotope** 的 session/harness/environment、异步执行、存储、部署与恢复边界 |
| 应用内 harness / SDK | OpenAI Agents SDK | 可由 Chronotope 承载或集成；SDK 的状态管理不自动等于托管运行、外部效果对账或产品身份 |

上述名称均已核实对应产品：`dots` 是 OpenAI 的个人长期代理，Muse 指 Meta Muse，Cue 指 Manus 的独立应用。Grok Bot / Team Bots、X 的 `@Grok` 和 xAI Multi Agent API 必须分别讨论。

面向本项目按对象分工：**Bots 拥有组织 Bot 的原生知识、工作能力与治理；外部应用拥有其协作界面及自有对象/规则/权限；Chronotope 提供执行、持久存储与隔离。** 类比 iPhone 内置 app 与安装的 app：Bot 可以自己设闹钟、记笔记、建待办，不必先在会议或工单系统建对象。共享频道、DM、context 与物理安全域仍分别治理。

## 3. Anthropic：团队产品与托管平台分别借鉴

### 3.1 Claude Tag：共享 Agent 及个人连接器

已读来源：[发布公告](https://www.anthropic.com/news/introducing-claude-tag)、[当前 overview](https://claude.com/docs/claude-tag/overview)、[Personal connectors in channels](https://claude.com/docs/claude-tag/concepts/personal-connectors)。

公告写明 “Within a given Slack channel, there’s one Claude that interacts with everyone.” 当前 overview 标 Public Beta，面向 Team/Enterprise，不支持个人套餐或第三方部署；频道内不要求每位 Slack 用户都有 Claude seat。工作 sandbox 按对话活动建立，idle 后释放，说明长期产品身份不依赖永久保留某个容器。

**必须修正旧材料的绝对化结论：个人 connector 现可用于本人发起的 channel/group-DM 请求。** 其他人在同 thread 的消息可作资料，但不能借此指挥请求者的 connector；autonomous routines 不使用个人 connector。

首次使用可选择 Allow、Allow with review、Don't allow，并可保存未来选择。Allow 仍有敏感筛查，但原文明言 “a screen, not a guarantee”；Allow with review 则每条结果人工审阅。结果可公开到频道，详细工作 session 仅请求者可开；服务**不检查每位频道成员是否具有同等源服务权限**。因此不能将“按个人源权限读取”误写为“结果自动符合频道受众权限”。

**对 Bots 的取舍**：管理员配置组织 Bot 的应用账号、能力范围和 session 策略；成员的个人授权、业务审批及分享 UX 由外部应用/授权方办理。Bots 仅消费有权委派引用，并由实际工具/sender 边界复验。借鉴请求者与执行身份分离，不建设成员个人 connector 产品；DM 与频道仅代表不同 session/data scope，不改变 Bot 的组织所有权。

### 3.2 Managed Agents：执行解耦与后台编排

已读来源：[2026-04-08 工程文章](https://www.anthropic.com/engineering/managed-agents)、[当前 overview](https://platform.claude.com/docs/en/managed-agents/overview)、[Multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration)、[Self-hosted sandboxes](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes)。

工程文章分别定义 append-only session log、模型/工具 harness loop 和 sandbox，介绍 `wake(sessionId)` / `getSession(id)` 恢复。当前平台 Beta 默认向 API accounts 开放；MCP tunnels 和 dreaming 额外申请 research preview，不能笼统写成所有多 agent 能力仍需白名单。当前不适用 ZDR / HIPAA BAA。

当前多 agent 包含 subagents、dynamic workflows、advisor，可组合 `multiagent_20261001`。subagent thread 可以持续 follow-up；dynamic workflow 的阶段线程在 run 结束前归档，不具有相同的后续对话方式。后台工作期间主线程可继续交互，支持“父处理消息，子做任务”的架构。

但各 agent 仅 conversation/event thread 分开，官方明确 **“All agents share the same sandbox, filesystem, and vault credentials.”** 工具 permission policy 不自动约束“启动哪个 run/inline agent”，启动准入、可用 agent 与预算需分别控制。不能将这套单 session 多线程直接作为不同长期 Bot 私态/凭据隔离的依据。

自托管 sandbox 是自托管 hands；**tool inputs/outputs 仍流经 Anthropic 控制面**，模型控制、skills 和 memory store 仍由平台承载。它不是完整平台自托管，也不自动满足载荷不离开客户环境。

### 3.3 Memory / Dreams：非模型改进最直接的工业参照

已读来源：[Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)、[Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)。

持久 memory store 可跨 session，支持 read-only/read-write、内容 hash precondition、不可变版本和历史 redaction；默认 read-write。官方明确警示注入内容可能进入 memory 并影响以后 session，不能因内容来自“记忆”就赋予可信指令权。

Dreams 属 research preview，输入既有 store 和历史 session transcripts，合并、去重、更新过时/矛盾条目并提炼 insight；关键合同为 **“The input store is never modified.”** 这只说明 dream job 不写输入，不证明其他 session 不能并发写输入 store。输出另一份普通 store，由调用者审阅后 attach 或 discard。

输出 ID 在运行中即可存在；failed/canceled 后也可能保留 partial 输出。cancel 状态改变不证明在途工作/usage 已完全停止。**看到 store ID、job 完成、模型自评变好，都不等于候选可以发布。** 文档未建立独立 holdout、自动 promotion、harness 代码自改、质量单调改善或完整来源删除闭包的合同。

**采纳形态**：冻结有权输入 revision/水位 → 隔离候选知识/经验制品 → Bots 评测与批准 → Bots owner CAS 切知识视图 → Chronotope 冻结引用。Bot 可形成真正的新业务知识和技能，不限于缓存；输入冻结/CAS 是本项目新增合同。原生 BotTask/Commitment 有自己的账本与验收，不能被整理覆盖；外部系统对象保持原权威。普通记忆积累是日常写入，行为方法变更才走受控晋升；来源生命周期仍按依赖关系作用于内化资产。

## 4. OpenAI：API、SDK 与 dots 的不同权威

本节依据 OpenAI Docs 技能检索并读取官方文档，页面未提供发布日期的内容不推断首次发布时间。

### 4.1 Agents API 与 Agents SDK

已读来源：[Agents API overview](https://developers.openai.com/api/docs/guides/agents-api/overview)、[SDK running agents](https://developers.openai.com/api/docs/guides/agents/running-agents)、[API multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent)、[Self-hosted environments](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted)。

Agents API 托管 Codex harness，由 OpenAI 管 sessions、orchestration、compaction 和 recovery；核心对象为 Agent / Environment / Session / Events/items。SDK 则在应用内运行 model→tool→handoff 循环，可由应用保存 history、使用 SDK session、Conversations API 或 `previous_response_id` 等状态策略。二者不能混为一个“OpenAI Agents 支持持久化”的功能格。

API 子 agent 有独立 context，可 create/message/wait/interrupt 并行工作；但父子共享 environment filesystem，并继承 MCP 工具、凭据与允许工具，当前子 agent 不支持 function tools。环境共享与权限继承是实质集成约束；若需求是互不信任的 Bot，需额外划分环境和受控工具访问。

自托管环境使用 `codex exec-server` 经出站 WebSocket 接收云端 harness 命令，应用承担环境生命周期和文件保留。主 API key 应在环境外，环境内受限 connection key 仍可能被生成代码读到。当前 Agents API 仅支持美国数据驻留、无 ZDR，执行面自托管不改变这一点。

**对 Chronotope 的选择**：SDK/harness 可作为平台控制模型/工具操作的实现；托管 Agents API 是具有自己执行 owner 的外部服务。后者不能伪装成内部每次模型/工具派发都可拦截的 local harness。如果硬约束无法由 provider 兑现，则拒绝该部署模式或明确采用受限的外部服务合同，不能双重自动恢复同一副作用。

### 4.2 Events 恢复与真实效果恢复分开

已读来源：[Events and items](https://developers.openai.com/api/docs/guides/agents-api/sessions/events)、[Errors and recovery](https://developers.openai.com/api/docs/guides/agents-api/errors)。

Events 是实时更新，items 是保存记录；root 与 subagent 的 item history 分开。重连采用先连 stream 并缓存、拉 saved items、按 item ID 合并。保存记录不覆盖所有错过的中间事件；stream closed、idle 或 turn completed 也不证明目标达成。

官方明确 **“A failed turn may already have changed files or called external tools.”** 恢复先 query session/turn/items，再检查已发生动作，之后有限重试/继续；failed session 有时需新建。重新建立产品视图不代表外部动作可以安全重做，也不证明任意工具 exactly-once。

这强化既有设计：运行状态、业务完成、消息接纳、provider receipt 与承诺履约分别记录。跨 provider 切换也不能仅把同 operation ID 发往另一个幂等账本，旧 attempt/unknown 仍由原 owner 对账。

### 4.3 dots：个人主体进入共享场所

已读来源：[Meet dots](https://learn.chatgpt.com/docs/dots)、[Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)、[Enterprise admin guide](https://learn.chatgpt.com/docs/enterprise/dots-admin-guide)。

同一 dot 跨 ChatGPT、Slack 和 Teams 延续长期责任与 notes，有自己的云端 computer/browser，可委派并行背景任务、生成独立可见 task threads、pause/wakeup；云端工作可在客户端关闭时继续，连接本地电脑的工作仍需设备在线且 ChatGPT app 打开。conversation context、ChatGPT memory 与 dot notes 分开；notes 不是完整 transcript，可跨渠道使用不等于可向更宽受众披露。

关键差异：**只有 owner 能通过 Slack DM 或受支持 mention 指挥自己的 dot**。其他人的消息不启动工作；owner 将 dot 带入 thread 后，其他消息可以作上下文。它不同于 Tag 的多人共享 Claude，不宜只按“均支持 Slack”归为相同产品。

proactive research 限于读信息和写私有 notes，不能直接发送消息、修改 apps 或控制电脑；schedule 和 event monitoring 另外设定。管理员分别配置 dots access、Slack participation、local computer、apps/actions 与 custom rules，已有企业 model defaults/controls 不自动套用 dots。断开 app **不会删除已取得 saved memories**。

**采纳**：跨入口身份、原生 notes/任务和后台跟进可作为 Bot 内置能力；Bots 配置组织所有权、session、账号与治理上限，成员交互仍在外部应用。dots 的个人 owner-only 不映射为 Bingdi 的个人 BotOwner。Bot 自建任务无需先有外部工单，内部验收与外部对象状态分别保存；撤连接和撤已存数据分开。官方资料未证明 dots 使用公开 Agents API，也未建立其自改进发布闭环。

## 5. Grok：长期 Bot、Team Bot 与 API 多 agent 分开

已读来源：[Grok Bot overview](https://docs.x.ai/grok-bot/overview)、[Team Bots](https://docs.x.ai/grok-bot/team-bots)、[Chat and collaboration](https://docs.x.ai/grok-bot/chat-and-collaboration)。

个人 Bot 有名字、职责、跨 session memory/files/browser/preferences，桌面和移动端访问同一主体；同账号 Bots **共享电脑、文件和 browser logins**。通用 Grok Bot 原生 group chat 教程可选 2–6 Bots，支持定向 @、reply、@everyone 与异步 Bot→Bot 唤醒；管理员可关闭跨 Bot 消息。所读材料未明确保证多个 Team Bots 按同样方式组成 group，2–6 也不是 Slack 同线程 Bot 数量上限。这些是产品协作依据，不自动给出持久 mailbox、父子 DAG 或迟到结果 fencing 合同。

Team Bot 是 “one Bot that your whole team talks to”：每人私聊独立，owner 不能读队友聊天；个人 notes 可跨 app 私聊/Slack DM 跟随本人。team memory 只在明确要求全队知道时写入并告知；owner/managers 改共享 skills/setup，普通成员教的新流程先留私人 notes。

每个 Team Bot 有自己的 Slack App，可邀请多个 channels，@mention 后 follow thread，每 thread 一个 conversation；仅响应已关联身份且在团队中的用户，workflow/其他 app 入口另有例外，不能仅凭 usage 计 owner 推断完整执行授权。OAuth plugin 用请求者账户；key/token plugin 用 Bot 共享凭据，应视为给全队的访问。共享对话使用个人 connector 时有单次或持久同意选择。

已读来源：[Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)、[Computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)、[Security](https://docs.x.ai/grok-bot/security)。

支持把成功任务或最长 10 分钟 browser demonstration 变为 skill draft，并要求审核、补失败处理及测试；routines 可定时/事件触发，客户端关闭仍运行。但 **Test run 会做真实动作**，不能当本项目无副作用 shadow。通用指南的每 Bot 50 routines、每 routine 20 次运行记录、最短 5 分钟调度是产品限制；本轮未核实 50 的计数在 Team Bot 中按个人实例还是全队聚合，不将其拼成团队配额合同，也不硬编码为我们的运行时上限。Team Bot routine 仍为个人所有、按个人执行/回报，不是全队共享任务身份。

owner 私聊、队友私聊分别用个人 computer；共享 channels/group DMs/threads 用该 Team Bot 的一台共享 computer。不同 screen 不是安全边界；同 Bot 的 screen 同时只跑一个 computer-use task。Reset 从最后 saved snapshot 恢复，近期修改可能丢失；durable disk 与 conversation/memory、运行进度不可混为一个恢复保证。

安全页当前明确写 **“Grok Bot runs only on Cursor-hosted cloud computers”**，并说明不支持 on-prem、own perimeter 或 BYO image；本轮保留该原文，不推导品牌/公司关系。私网路由不等于自托管。Auto Review 也不检查所有副作用，memory writes / 多数 settings 是文档给出的例子。

另读：[Tag @bot on X](https://docs.x.ai/grok-bot/tag-on-x)、[Multi Agent API](https://docs.x.ai/developers/model-capabilities/text/multi-agent)。`@bot` 将自己的帖子交给个人 main Bot，X 只简短确认，工作/结果在 Bot app；不是 `@Grok` 或所有人都能操纵的公共主体。API 的 `grok-4.20-multi-agent` 是 beta 的单请求 4/16 agents + leader 汇总，与长期 Team Bot 的主体、私态 ACL、渠道身份分别成立。

**采纳**：session 数据隔离、共享技能治理、示教生成 draft、异步 handoff 和固定工作流执行身份。Grok 的个人所有权和聊天 UI 不照搬；组织 Bot 可有原生知识、目标和触发，自主创建工作与调度。涉及外部应用自有对象的触发条件、资格和目标则尊重该方规则，不以 persona/screen 证明隔离，也不把 skill 保存或 Auto Review 当完整发布审计。

## 6. Meta Muse：个人长期目标与独立权限执行层

已读来源：[2026-09-08 发布公告](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)、[当前产品页](https://ai.meta.com/muse/)、[How We Designed Muse](https://introducing.muse.ai)、[How We Built Safety Into Muse](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)。

产品以个人长期对话、可命名人格和 Goals 为主，可中断/同时派发多个任务、建立 side chats、在关闭 app 后按 schedule/事件工作，并仅在有意义更新或需要输入时通知。memory 文件可以读/改；多 subagents、定制工具和技能是公开描述，但不等于经过独立评测的自主发布。

最值得借鉴的是安全工程的**职责分离**。个人 Muse Secure VM 内，harness 和生成代码处于非特权 runtime cell；host 侧独立 Sentinel 是 connector action 和网络 egress 的权限权威，`authd` 管 credential store 与 surrogate，受限 `privsep` workers 执行内置 connector。所有外部请求经过独立边界，不能靠改 skill/CLI 或 agent 自述授权绕过。审批在独立 UI 中直接回到 Sentinel，不让模型从聊天文本自行创造 grant。

文章还描述 kernel/eBPF 的 tainted egress、具体网络目标与请求校验、浏览器 broker、用户接管时暂停 agent。这提供了工业分层依据，不是要求首版复制整套 VM、内核和分类器实现；当前应优先做统一工具/出站边界、受限凭据及可核对审批。模型/分类器判断仍会出错，官方明确 prompt injection 尚是开放问题。

数据方面，VM 是其应用 system of record，但必要 inference/telemetry 会出 VM；launch 架构不阻止 Meta 为运维/安全等访问数据。文章中的 Confidential VM 属计划/小范围测试，不能将当前 Secure VM 误写成厂商也无法访问。按产品说明可让 Muse 忘记信息，不等于公开证明了本项目要求的派生闭包和历史上下文抹除。

**归属**：可借长期目标、原生待办/调度、知识沉淀及独立执行门。Bots 的组织 Bot 能为自己的工作建计划、提醒和承诺；外部应用只对自己的业务对象/授权及规则负责。Chronotope 提供耐久调度和隔离。Muse 的个人 Goals UI 不照搬为成员聊天产品，但其原生工作能力不能因 UI 定位不同被排除。

## 7. Manus Cue：每个主体自己的入口与协作形态

已读来源：[2026-09-28 Manus 2.0 公告](https://manus.im/blog/introducing-manus-2-0)、[Cue 多 messenger 帮助](https://help.manus.im/en/articles/14178640-can-i-connect-multiple-messaging-agents-at-once-in-cue)。公告将 Cue 定义为独立 mobile/desktop 应用，与 Manus 共用基础设施；early access 凭邀请进入。

公告明确每个 agent 自有邮箱、电话号码、钱包、电脑，可接电话并留摘要；多个 agents 可进入共同目标 group，用户设方向并作最终决定。帮助中心确认**同一 Cue agent 可同时连接 iMessage、Telegram、LINE、Slack**，可逐个关闭或同时启用。这是“主体先于 channel”的直接工业参照，不能把一个 agent 定义为某条 Slack thread 的永久进程。

公告还区分 Manus Studio、Cloud Computer、事件 Automations 与 Cue。Manus 能被 Slack 消息/邮件等触发，不代表 Cue 的所有消息订阅、去重与恢复细节已公开。每个 agent “有自己的电脑”也不能仅凭文案推出硬隔离、任意 checkpoint 恢复或跨租户泄露保证。

**采纳**：组织 BotID 先于入口，多个应用账号/入口挂同一主体，session 与回复目标显式绑定。共享 group 和成员协作属于外部应用；Bots 管理运行配置和状态索引。个人电话、钱包、支付和日常服务 UI 不作为 Bingdi Bots 的产品路线。

## 8. 原生能力、外部应用与执行 Infra 的分工

| 优化 | 外部应用 | Bingdi Bots | Chronotope |
|---|---|---|---|
| 治理与业务准入分开 | 成员/客户等白黑名单、业务角色/规则、审批及决议 | 管理员配置组织 Bot 的人格、可用工具能力、参与/session 模式及发布 | 校验可信引用并执行治理与外部有效授权的共同约束，不从 mention 推导权限 |
| 应用账号与 Bot 身份分开 | 账号授权、业务资源权限、成员交互与披露批准 | 配置 Bot 的应用账号/委派引用，固定 loop 执行身份 | 凭据代理、当前 grant/epoch 和实际派发检查；外部拒绝不得换身份绕过 |
| 计算绑定显式化 | 提供允许访问的业务资源范围 | 配置 Bot/session 资源隔离，DM 不改变组织所有权 | 强制 workspace/volume/credential 实际边界，报告恢复水位/缺口 |
| 业务知识内化 | 自有记录/规则/权限及来源生命周期 | 内化的业务知识、经验、技能是 Bot 资产；保存自身记录/版本及适用性，普通积累不逐条发布 | 可承载持久 record/blob/index、lineage/失效、namespace 与 CAS；存储位置不改变语义 owner |
| 行为方法受控改进 | 涉及自有对象时提供权威验证 | skill/SOP/harness/memory 方法候选、原生任务验收器、独立评测和晋升批准 | 隔离 job、不可变来源/digest、partial 状态、通用 CAS 与受信版本生效 |
| provider 能力明确化 | 业务集成所需接口及限制 | 管理部署目标、配置和治理要求 | 区分 local harness/SDK/托管服务，维护唯一恢复 owner，能力不足显式拒绝/受限 |
| 原生工作与外部对象分开 | 自有会议/issue/订单/合同的 deadline、终态、业务规则 | BotTask/Plan/Schedule/BotCommitment 可自主建立、修订、验收，关联可选 ExternalWorkRef；成员交互仍外部 | 有限 activation、异步 child、timer/wait、claim、预算及结果/receipt；不把内部完成等同外部终态 |

Bots 对 Bot 自身及其原生知识/工作资产负责，可提供内置工具，不是只转发外部 API 的配置壳。SOP 使用内置知识、任务和调度，也可调用外部业务 API；涉及外部对象资格、名单和终态时尊重该方权威。普通已授权任务/闹钟创建不逐条走管理员发布审批，行为方法变更才进入晋升流程。

## 9. 后续参考场景与扩展顺序

以下均为能力参考，没有产品测试结果；表中 P0/P1 是该能力启用时的优先级，不替代当前期 8 G0/G1/G2 的 MVP 范围：

| 优先级 / 场景 | 验收依据与落点 |
|---|---|
| P0 · 企业治理与业务拒绝 | 管理员部署组织 Bot，成员只在外部应用交互；业务白黑名单在外部修改后按该方决议执行，Bots 不复制名单。拒绝后不得换账号/Bot/attempt 绕过。Bots C，infra B1/B3 |
| P0 · 隔离是否真实 | 两个 persona/child context 共享 volume 的测试要显式暴露共享；需要私态隔离的主体不能因不同 session 就共享登录；同 Bot 多 channel 不默认共享全部私有文件。B1/B4 与 Bots 配置 |
| P0 · 恢复不制造效果 | disconnect/reconnect、failed turn、新建 session 或换 provider 后，旧 operation/unknown 留原 owner 对账；snapshot 恢复明确近期变更缺口。A/B 既有合同 |
| P1 · 知识资产与整理 | 内化业务知识可独立存续、版本化及用于新任务，读取仍遵守来源/当前scope；partial 不晋升，知识视图 CAS 不覆盖原生任务或外部对象。Bots D1/D5，infra record/index/job |
| P1 · 常驻与自主任务 | Bot 自建计划/调度，不要求先有外部 task/calendar；创建受既有能力/预算约束，醒来后重验当前授权；新私聊不改变组织归属。Bots D2/E，infra wait/预算 |
| P1 · 会议闹钟 | 外部会议→Bot 自己的提醒→持久 wait→有权发送；改/删 Bot 闹钟不改会议，会议更新按任务跟随策略处理；重启不重发 unknown，提醒完成不等会议完成 |
| P1 · 管理面与交互面分离 | Bots 管理台配置/部署/暂停/审计，也可查看管理原生知识/任务/调度；成员仍在 Slack/GitHub/Linear 交互。DM session 隔离但 Bot 仍组织所有 |

先落地 A/B 执行机制，再建设组织 Bot 治理、知识资产、原生任务/调度、应用接入和受控改进。Bots 负责原生任务的验收，外部对象采用对应外部证据；工业产品与论文不能替代真实集成、故障 PoC 和实际质量验证。

## 10. 研究边界与后续跟踪

- 官方文档建立的是公开接口与用户约定，未公开 journal、fencing 或 exactly-once 不等于内部没有；Chronotope 的差异必须通过实际可检验合同证明。
- 没有将“长期记忆”“学习偏好”“保存 skill”“Dreams 整理”统一称为完整自主 RSI，更没有从中推导可自动改发布门或义务合同。
- 没有核实 dots、Tag 或 Muse 具体使用哪款公开托管 Agent API；产品与平台并列出现不建立实现依赖。
- rolling 文档、preview 和邀请访问可能继续变化，实施/采购前重新确认功能、地区、数据政策、配额及价格；本轮不做价格排名。
- 原[Agent SaaS 调研](../agent-saas-持久执行调研报告.md)保留为历史材料；其中二手资料、旧价格和广义市场判断不作为本轮结论依据。本文以当前官方资料校正个人 connector、多 agent、Dreams 和产品分层。
