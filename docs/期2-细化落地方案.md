## A. 工作区 blob 合同（RustFS 内容寻址）

### A.1 目标与现状

- **目标**：会话工作区从「沙箱卷（不透明）」演进为「内容寻址对象图 + 目录索引」——文件可按 hash 寻址、按文件增量同步、跨沙箱 dedup、销毁后可重建（无需快照卷 tar）。
- **现状**：/workspace 在 named volume；externalize 输出到 executor 宿主目录（本地文件）；快照 = 镜像 + 卷 tar（粗粒度）；`sandboxes.file_sync_state`（syncing/synced）字段已预留未用；RustFS 已在 compose 替代 MinIO（S3 9000，凭证 `chronotope/chronotope_dev（RUSTFS_ACCESS_KEY/SECRET_KEY）`）。

### A.2 设计

1. **存储布局**：RustFS bucket `workspaces`——`{org}/{session}/blobs/{sha256}`（内容寻址对象）+ `{org}/{session}/manifest.json`（目录索引：`path → {hash, size, mtime}`）。
2. **写路径（增量同步）**：executor 的 write_file（快路径）成功后 → 读文件内容 → sha256 → PUT blob（幂等，同 hash 已存在则跳过）→ 更新 manifest 行（新表 `workspace_files(session_id, path, hash, size, updated_at)`，UNIQUE(session_id, path)）；同步完成 → `file_sync_state = 'synced'`。
3. **读路径（恢复）**：CreateSandbox 的 RestoreFrom 支持 `blob:` 前缀（现有 `img|tar` 之外的第二形态）→ 从 manifest 拉取全部文件写回 /workspace；或按需懒拉取（read_file 时按 path 查 manifest → GET blob → 本地缓存）。
4. **与快照的关系**：快照卷 tar 保留（粗粒度、秒级恢复）；blob 合同是**细粒度增量**（按文件同步、跨沙箱 dedup、快照缺失时的重建来源）。checkpoint 的 snapshot_ref 继续优先，blob 合同为兜底与增量。
5. **MVP 剪裁**：只做 write_file/read_file 快路径的 blob 同步 + `blob:` 恢复（bash 命令产生的文件暂不入合同——外部效果只有文件工具可见面）；懒拉取后置（恢复时全量拉 manifest）。

### A.3 验收

- 单测：blob PUT 幂等（同 hash 跳过）、manifest 行 upsert、RestoreFrom blob: 解析与拉取。
- e2e：写文件 → 断言 RustFS 有 blob 对象 + manifest 行 → **销毁沙箱（无快照）** → 新沙箱 `blob:` 恢复 → read_file 同内容——「快照之外的第二条恢复链」实证。
- 现有 w2-snapshot e2e 不回归（快照链仍优先）。

### A.4 风险

- RustFS 凭证硬编码 → 环境变量注入（`RUSTFS_ACCESS_KEY`/`RUSTFS_SECRET_KEY`，compose 已预留 MINIO_ROOT_* 兼容位）。
- 大文件同步延迟 → blob PUT 在工具返回后异步（同步失败不阻断 run，state 标记 `syncing` 重试）。

## B. 冷层归档 + usage 增量 rollup

### B.1 目标与现状

- **目标**：① 老会话的事件/消息冷归档（RustFS `archives/` bucket + 清单），投影固化后可删热数据；② usage 从「全量重建」改「水位增量累加」（幂等、规模化前提）。
- **现状**：导出 tar 是人工按需的（无自动归档）；usage 桶由 api 聚合器全量重建（正确性 OK，规模化痛点）；无归档清单。

### B.2 设计

1. **归档**：worker 周期任务（或 api 手动触发 `POST /sessions/{id}/archive`）——条件：会话 `archived_at` 为空且最后事件 > 30 天（可配）→ 导出 events.ndjson.gz + messages.ndjson.gz + manifest.json 到 `archives/{org}/{session}/` → 写 `archives` 表行（session_id, bucket_path, counts, created_at）→ 更新会话 `archived_at`。**MVP 不删热数据**（归档为冷读副本 + 证据）；删热数据后置（需物化回放链路验证后）。
2. **按需物化**：`GET /sessions/{id}/archive` 返回清单 + 拉回事件（api 从 RustFS 读——api 需要 S3 客户端或经 executor 代理；MVP：api 直连 RustFS S3，凭证 env）。
3. **usage 增量 rollup**：聚合器每次 tick 记录水位（max(events.id) 已处理）→ 本次只累加水位之后的新事件（delta）→ 水位持久化（表 `usage_watermark(org_id, bucket_ts, last_event_id)`）→ 幂等：同水位重跑 = 无增量。崩溃恢复：水位未推进 → 重放 delta（事件幂等键防重）。
4. **MVP 剪裁**：先做 usage 增量（收益直接、改动收敛在 api 聚合器）；归档链路随后。

### B.3 验收

- 单测：增量 rollup 幂等（同水位重跑两次 → 用量不变；新事件 → delta 累加）；水位推进。
- e2e：跑 run → 聚合 → 用量正确；注入新事件 → 下一 tick 只加 delta；手动归档 → RustFS 有 gz + 清单行 + GET archive 可见。

## C. 控制台时空视图（分支 UI）

### C.1 目标与现状

- **目标**：控制台把时间旅行暴露给人——checkpoint 标记、fork/rollback 操作、diff 简视图、分支血缘。
- **现状**：API 四端点已就绪（checkpoints/fork/rollback/diff）；控制台有时间轴回放/记忆面板/审批按钮（Next.js）；无任何时间旅行 UI。

### C.2 设计

1. **时间轴 checkpoint 标记**：SSE 时间轴渲染 `session.checkpoint` 事件为竖线标记（hover 显示 seq/快照 ref）。
2. **操作按钮**（会话页头部）：`创建检查点`（POST checkpoints → toast 显示 id）、`回退`（选择 checkpoint → confirm → POST rollback → 时间轴刷新出现 rolled_back 标记）、`Fork`（选择 checkpoint → POST fork → 跳转新会话页）。
3. **diff 简视图**：会话页「对比」下拉选择分支会话 → GET diff → 两张事件清单（公共前缀折叠、OnlyA/OnlyB 各列）。
4. **分支血缘**：会话页显示 `forked_from_session` 链接（面包屑回父会话）；MVP 不做 run 树拓扑图（数据已在事件轴可算，UI 复杂度高——后置）。
5. **验收**：Playwright e2e——fork 按钮 → 新会话出现在列表且血缘可见；rollback → 时间轴出现 rolled_back；diff 视图显示两侧差集。
