## ⑧ 冻结变化输入：journal 确定性输入快照

**问题**（评审子项仍成立部分）：`buildMessages` 每轮读 messages 表、org 预算检查每步读可变用量（其他会话的消费会使重放看到不同值）、部分路径读墙上时间——journal 失效后的重新执行可能走入与首次不同的分支。

**已确定的确定性事实**（设计依据）：
- harness 调用本身是 journaled Run（请求全量入 journal，缓存命中不回发）——消息窗口已随 journal 固化；
- 会话消息单写者（worker 独占）+ 双开 409 + `004_message_dedupe` → 同一 run 的重新执行读到的历史**不会变**；
- 活跃秒已 journaled（`execOutcome.duration_ns` 回放同值）；scheduler 定时器 journaled。

**剩余非确定源**：org 日用量在 run 执行期间被**其他会话**推进 → 每步配额检查点在重放时可能判超限 → 冻结分支与首次不一致。

**设计**：run 级预算检查基于「run 入口快照 + run 内累计」（确定性），org 实时性由下一个 run 的入口重新快照兜底——
1. run 入口（首个检查点）把 `GetOrg 配额 + OrgDailyUsage` 快照 journal 化（`restate.Run(WithName("budget-snapshot"))`）；
2. run 内每步检查 = 快照用量 + 本 run 累计 token/计算秒 > 配额 → 冻结（不再读库）；
3. 冻结语义不变（awakeable 槽/充值解冻）；下一个 run 入口重读真实用量。

**验收**：
- 单测：执行中改变 store 的 org 用量 → 重放仍走与首次相同的分支（预算快照生效）；
- 单测：第二个 run 的入口读到新用量（实时性兜底生效）；
- 全量 CI 回归（w5-budget e2e 3 项不回归）。

## ⑨ ComputeLease：沙箱依赖安全释放 + generation

**问题**（评审仍成立）：沙箱是 sleep-infinity 容器 + 按 created_at 的 TTL GC——等待/挂起的计算没有 lease 释放合同；回收不按资源依赖安全决策；无 generation fencing。

**设计（MVP 剪裁：lease 账本 + 依赖安全回收；fencing 并入 ⑩ 统一做）**：
1. **租约账本**：`migrations/010` 加 `sandbox_leases (sandbox_id PK, run_id, generation bigint, expires_at, created_at)`；executor 协议加
   - `POST /sandboxes/{id}/lease` `{run_id, ttl}` → acquire/renew（UPSERT 重置 expires_at，generation+1）；
   - `DELETE /sandboxes/{id}/lease` `{run_id, generation}` → 释放（generation 不符拒绝——防旧持有者误释放新租约，fencing 的最小闭环）。
2. **依赖安全回收**：GC 回收条件改为「TTL 过期 **且** 无未过期 lease」；挂起/冻结的 run 由 worker 在每步检查点 renew lease（harness 调用前后 + 工具执行前后）——run 活着（含挂起）即持有；run 终态（completed/failed/canceled）release。
3. **worker 接线**：runLoop 每步 `renewLease`（journaled，防重放重复续约——journaled 后重放回放同续约，安全）；run 终态（含取消/失败路径）`releaseLease`。
4. **fencing 最小语义**：lease 带 generation；executor 的 execute 拒绝「lease 已过期」的沙箱（409）→ worker 走既有 ErrSandboxNotFound 重建路径的扩展（lease-expired 哨兵 → 重建）。

**验收**：
- 单测：acquire/renew/过期判定、generation 不符释放拒绝、GC 跳过有 lease 的过期沙箱；
- 单测：execute 对无 lease 沙箱 409 → 重建重试；
- e2e：挂起审批的 run 其沙箱在 TTL 过期后仍存活；run 终态后释放 → GC 回收（扩展现有 w2-snapshot/GC 场景）。

## ⑩ accepted spec digest + 版本绑定 + 旧 run 路由

**问题**（评审仍成立）：无 accepted spec digest；agent 升级（version+1）后旧 run 重放读到**当前** config → 分支变化；无旧 run 路由。

**设计**（落地方案 §15「版本绑定在 run 上」的兑现）：
1. **config spec digest**：`createAgent/updateAgent` 时计算 `sha256(canonical JSON(AgentConfig))` 存 `agents.spec_digest`（迁移加列）；`agent.version` 仍递增。
2. **run 绑定快照**：`submitRun` 建行时把 `{agent_config 全量快照, spec_digest, protocol_version}` 写入 `runs.bound`（已预留 jsonb）；run.started 事件携带 digest。
3. **runLoop 读快照**：runLoop 不再从 session state 读当前 AgentConfig，改为读 `run.bound.agent_config` 快照（会话 state 仅作槽位/成员/MCP 等会话级状态）——**旧 run 重放永远用其启动时的 config**；group 成员/MCP 连接属会话级（参与者变化对旧 run 可见，符合群聊语义——文档注明该边界）。
4. **accepted spec 校验**：runLoop 入口校验 `bound.spec_digest == agents.spec_digest`？否——**不校验**：旧 run 就该用旧 config 跑完（路由语义），digest 仅作审计与调试关联；「拒绝不匹配」只发生在**新 run**（api 层按当前 digest 建行）。
5. **harness 协议版本路由**：run.bound 记录 protocol_version；harness 请求带之（已有字段）——正式版 harness 多版本共存时按 version 路由；MVP 单版本下仅作断言。

**验收**：
- 单测：agent 升级（version+1、config 变更）后，旧 run 的重放仍用旧 config（runLoop 读 bound 快照）；
- 单测：新 run 绑定新 config + 新 digest；
- 单测：digest 计算确定性（同 config 同哈希；字段顺序无关——canonical 序列化）；
- 全量 CI 回归（demo 15 阶段不回归；群聊/子 Agent 的 config 传递链验证）。
