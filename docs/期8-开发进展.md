## 当前门禁与历史场景

- GitHub CI 的 Go 工具链从 `go.mod` 读取；默认 e2e 与 `scripts/ci.sh --e2e` 共用 `scripts/demo.sh`，只运行更新后的 W1（创建幂等键、真实 202 接纳、GET 终态）及 application runtime 的完整 fake HTTP 模型/工具/timer/进程恢复门禁。
- `workflow_dispatch.run_real` 只运行真实模型的 application runtime 门禁，缺少所需模型凭据明确失败；不包含真实 E2B、Slack 发送或最终 provider receipt 的验收。fake 与 real 报告分别保存，未实际运行不能记作通过。
- 历史全场景保留在 `scripts/demo-legacy.sh` 和旧 `test/e2e/`；GitHub 仅通过显式 `run_legacy` 手动选择诊断 job，保留原断言和失败状态，不属于当前 C0–C3 的默认门禁或通过证据。
- 旧脚本尚未全量适配创建必需 key、异步 run 与模型工具 alias；迁移需要逐场景区分 HTTP 等待方式和实际功能差异，不能用 curl 拦截、伪造 201/终态或放宽断言替代验证。本期不批量迁移所有历史场景。

只读估量（不是运行验收）：排除已更新的 W1/helper，45 个历史 Shell 场景包含 51 处 agent、63 处 session 创建调用，114 处均缺创建 key；其中 42 个脚本包含 78 处已有 key 的 run 提交，另有一处内嵌 Python 提交。完整迁移涉及数十文件，不能视为一次机械替换。

已确认的额外差异：旧 MCP 清单仍以 `mcp:server:tool` 作为模型名，会被新 Python alias 校验拒绝；旧 dispatcher 未承接已删除内联执行的 `http_request/web_search`；部分 SDK adapter 的异常帧仍用 `payload.error`，与 `code/message` 合同不符。这些需要真实实现或范围决策，增加等待 helper 无法修复。当前 legacy loop 已先处理 tools 再处理 done，不将此前这一风险继续列为现存缺陷。

可先按需迁移普通无工具场景：创建使用每个逻辑资源独立的稳定 key，完整 run 显式 `run_and_wait`，保持原业务断言。幂等重放的 200、busy/限流的 409/429、只观察审批/冻结等挂起场景继续直接断言 HTTP/等待证据；摘要、通知、SSE 等还须等待各自衍生结果，不能把 GET completed 当成全部副作用完成的屏障。旧场景本轮未全量运行。
