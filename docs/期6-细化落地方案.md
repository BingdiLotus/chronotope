## 二、材料中的不合理设计（必须指出）

1. **「replay 是反模式」不适用于本仓库**：Holon 批评的是「把对话历史灌回
   上下文窗口」（transcript → context）；Chronotope 的 journal 重放是
   「decision → effect」的执行引擎语义（不进模型上下文、每步 <10ms）——
   评审已正确区分，此处确认不采纳 Holon 的 replay 批评。
2. **「零成本等待」是声称不是实测**：Holon 全文无 benchmark（唯一数字是
   设计估算）。方案落地时须实测（durable sleep 的每唤醒开销），不照搬
   「零计算成本」的宣称——写进验收。
3. **「一条改动三个诊断收敛」过度**：WaitFor 收敛（表+原语）、intent 捕获
   （字段+捕获点）、信任拓扑（标记+策略）是**三处独立改动**，共享同一哲学
   但不是一条 commit 能收敛的。

## 三、方案（期 6 三段）

### §A WaitFor 具名原语（四种唤醒底座的收敛）

**现状**：四种底座齐备但分散（restate.Sleep / child run 管道 / outbox /
awakeable+digest）——各走各的语义。

**改动**：
- 028 迁移 `session_waits` 表：session_id / kind（timer|task_result|external|operator_input）/ handle / intent / expect / registered_at / resolved_at
- `WaitFor` 收敛：runLoop 的四处等待统一走「注册 WaitHandle → 零成本挂起 → 唤醒查 handle → 判定」——与 M2 的 DECIDE 衔接（「唤醒即执行」→「唤醒→查 WaitHandle→判定」）
- 唤醒路径的判定复用 M2 的 Decide（每唤醒先查「在等什么、条件是否满足」再决定 run/wait/quiet）

**验收**：四 wake kind 各一条 e2e 断言（timer 退避/task_result 续跑/external 路由/operator 签核）+ 每唤醒开销实测（「零成本」的本地数字）

### §B yield intent 捕获（「为什么停」的一等对象）

**现状**：journal 记录发生了什么，不记录为什么停——「我上次为什么停」
需从事件流推导（决策蒸发的根）。

**改动**：
- pending 状态（session_waits 的 intent/expect 字段）随 WaitFor 一起持久化：
  假设了什么（「假设 CI 30 分钟内绿」）+ 期待的返回条件（「reviewers ≥ 2 且
  无 change request」）
- causal slice 注入：buildMessages 的冻结切片加「上次为什么停 + 在等什么」
  段（恢复时进上下文而非 transcript——与 M2 的请求冻结衔接）

**验收**：挂起→恢复的 run 载荷含 intent 片段（e2e 断言）+ 决策蒸发的反例
（恢复时无需重新解释为什么停）

### §C 信任拓扑（ingress 的内容级信任标记）

**现状**：工具级 allowlist（MCP）+ 动作级审批（risk class + digest）——
**缺入站数据的内容级信任标记**（webhook payload 与操作员指令在进入上下文时
无信任差异）——prompt injection 的缺口（两篇文章之外的新增）。

**改动**：
- ingress 的 trust 标记：`untrusted_data`（webhook/不可信 issue/MCP 返回）
  vs `operator_authority`（认证控制台）
- 规则：**低信任内容不能授权 class 2 动作**（不可改变根目标/批准破坏性
  操作——除非显式提权）——risk class 的信任参数（class 2 的审批要求
  操作员信任级别的输入）
- causal slice 组装时标记来源信任等级——模型可读作证据，运行时强制边界

**验收**：prompt injection 反例测试（不可信 payload 的越权指令被拒）+ 安全
白皮书章节（docs/安全-信任拓扑.md——直接面向销售材料）
