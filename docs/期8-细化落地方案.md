## 2. 最小能力与契约

接口字段和交付边界统一见[应用接入契约](./应用接入契约.md)。它是本期目标，不表示端点已存在。

### 2.1 Agent、session 与 run

- agent/session 创建使用稳定客户端幂等键和规范请求摘要。同键同请求回原 ID，异请求冲突，支持调用方修复“远端创建成功、本地关联未存”的窗口。
- runtime agent 配置作为不可变快照使用，run 绑定实际版本、模型、工具和执行身份。应用管理其产品版本与 session 路由，不新增跨 provider 发布管理器。
- run/command/admission outbox 同一 PG 事务接纳后返回 `202 + run_id`，dispatch/recovery 不同步等待长 run。
- 同幂等输入重试优先返回原 run；新输入遇 session busy 可返回 409，由应用持久排队，不静默丢弃。
- `GET /runs/{id}` 校验归属，返回 canonical status/final/error/usage；终态与结果原子可见。应用不必依赖活 SSE 连接才恢复状态。

### 2.2 模型与应用工具

- 一段只做一次实际模型请求，输出本轮全部 calls 和终态/usage；worker 按确定顺序 dispatch，再组装完整 assistant/tool 历史。
- 工具的描述、schema、model alias 与内部引用固定一一对应；无效 JSON/参数回喂错误，不静默替换 `{}` 执行。
- bridge 目的地址及服务认证来自受信配置；context 从 bound run 派生，不由模型 arguments 填写。内核只解释通用 tenant/scope/操作身份，产品主体以 opaque subject_ref 传递。
- 同 step/call 的结果与操作身份可重放。工具接收方承担实际业务写入幂等/原返回值持久化；内核不把 RPC request ID 当业务去重保证。
- 本期应用 profile 不开放任意 HTTP、shell、浏览器或其它 SDK adapter。未被暴露的能力不要求先建完整沙箱/网络治理平台。
- 模型输出 token、调用/steps 与 run deadline 是派发门；provider 请求 timeout 取剩余时间。usage 是事后计量，不充当硬预算。应用自己的任务数量/并发配额归应用。

### 2.3 通用 timer

- `POST /timers` 持久接纳稳定 timer ID/revision、绝对 due_at 和 opaque action ref 后返回 202；同 key 同请求返回原 handle，异请求冲突。
- 创建状态和待提交责任持久化，启动 workflow 使用稳定 key；不得先应答成功再只靠内存 goroutine。
- 复用 Restate 可重放时间和 Sleep；过期输入立即触发，不周期调用模型。timer 独立于聊天 session，不调用 SchedulerPolicy 决定要不要丢弃一次性唤醒。
- 回调地址来自固定应用配置。fire ID 和 payload 稳定，网络/响应未知可重投；只有应用耐久接纳后 ACK 才完成这一跳。错误和未接纳状态可查询，不静默清除投递责任。
- 任务改期/取消是否有效由应用最终 claim 校验 revision/status；旧 timer 到达可被应用幂等忽略。主动中断旧 Sleep 是资源优化，不先建设通用调度编排器。
- timer fired 只证明应用接纳了唤醒，不能推导业务完成、最终平台发送成功或已读。

## 3. 本仓库实施顺序

| 批次 | 改动 | 完成证据 |
|---|---|---|
| C0 | 单次推理、全部工具/错误回喂、schema/alias、HTTP bridge、实际开放路径授权 | 模型不知道的 nonce 工具结果真正进入下一请求；一轮两工具均执行；非法主体/参数被拒 |
| C1 | 创建幂等、run 异步接纳、dispatcher/recovery、结果查询与终态幂等 | 事务提交后杀 API 能重投；同 key 返回原 ID；busy 不破坏旧 run；completed 不缺结果 |
| C2 | 通用 timer 接纳/稳定 fire/固定回调/状态与重投 | 等待中重启 worker 仍触发；回调落账后响应丢失可重投；同 key 异输入冲突 |
| C3 | 与 Bots 参考应用联调，固定服务/模型/镜像版本 | 支撑 Bots G0/G1 的真实模型→应用工具→timer→回调链；最终 Slack 结果由 Bots 验收 |

不要把 C0–C3 扩成全资源 RBAC、通用 Record、完整 MCP/A2A、长 actor、多 Agent、跨版本 journal 接管、HA 或自动 RSI 平台。原生知识/任务的价值验证在 Bots 仓库，不在这里复制一套验收器。

## 4. 必须保留的故障与限制

| 场景 | Chronotope 必须证明 |
|---|---|
| agent/session/run 已创建，响应丢失 | 同 key 查询/重试返回原资源，无第二个对象 |
| run 已入 PG，尚未被 Restate 接纳 | outbox/recovery 可恢复派发，不能同步堵塞所有待处理项 |
| 多工具与错误结果 | 全 calls 保留，success/error 都带原 call ID；不丢工具、不重复回放历史 |
| 已知模型结果但 usage 缺失 | 保留已知结果并单列计量未知，不伪装成结果未知重做 |
| timer 等待时重启；到点回调响应丢失 | 仍唤醒，重复 fire 保持同身份，应用可幂等接纳 |
| 跨 tenant/scope 使用资源 ID | 本期开放接口和 bridge 拒绝，不只依靠模型指令或外层路由 |
| 达输出 token/steps/deadline 上限 | 显式停止/拒绝新的派发，结果和已知外部效果仍留痕 |

外部应用调用一旦未知，内核只保存实际已知状态；不能以新 attempt/RPC ID 暗示副作用未发生。参考应用最终 sender 的 unknown、receipt 和 task 状态分别由 Bots 管理，见其主合同。

代码变更后跑相关单元/PG 集成和故障测试，再跑适用的 `scripts/ci.sh --e2e`；被删除旧路径的契约/样例随代码同步更新，不保留兼容分支。缺凭据、跳过和真实路径未验证必须单独记录。

开发重建在本仓库执行 `docker compose -f deploy/docker-compose.yml down -v`，新代次重新初始化 PG/Restate/对象存储和应用 schema。它不替代保留卷的同版本恢复测试，也不会撤销已发出的外部消息。本轮只迁文档及初始化 Bots，未执行清库或更改运行时行为。
