# 应用接入契约：有限运行、工具与通用 Timer

> 2026-10-21。应用契约 v1.0.0：C0–C3 接口、执行路径及参考验收已完成；P0 增加契约 fixture/CI、稳定错误码、结构化观测和动态 target。实际证据及历史边界见[开发进展](期8-开发进展.md)。
> 机器契约与错误集合见 [application-contract.v1.json](contracts/application-contract.v1.json)；错误映射见[错误分类与可观测性](错误分类与可观测性.md)；动态 target/fencing 见[动态 target 注册与 fencing](动态-target-注册与-fencing.md)。
> Chronotope 提供执行机制。应用拥有自身对象/策略/队列和最终验收；Bots 的消费行为以[Bots MVP](../../bots/docs/MVP设计.md)为准。

## 1. 控制接口

| 能力 | 目标接口及结果 |
|---|---|
| 创建不可变 agent 配置 | `POST /orgs/{org}/agents`；带稳定 Idempotency-Key，返回 agent ID/config digest |
| 创建技术 session | `POST /agents/{agent}/sessions`；带稳定 Idempotency-Key，返回 session ID |
| 接纳有限 run | `POST /sessions/{session}/runs`；同事务保存 command/outbox，返回 `202 + run_id` |
| 查询结果 | `GET /runs/{run}`；status、final/error、usage 和 bound 配置引用；终态与结果同一提交后可见 |
| 接纳单次 timer | `POST /timers`；tenant/subject/scope + timer_id/revision/due_at/opaque_action_ref，返回 `202 + timer_handle` |
| 查询 timer | `GET /timers/{timer_id}?tenant_id=…&subject_ref=…&scope_id=…&revision=…`；返回提交/回调状态、稳定 fire_id、`last_error` 与机器码 `last_error_code` |
| 管理动态 target | `POST/GET /orgs/{org}/application-targets`、`DELETE .../{kind}/{ref}`；仅平台 operator，静态 env 继续可用 |

幂等键均在受权 tenant/资源命名空间内解释；同键同规范请求返回原 ID/result，异请求拒绝。查询幂等结果先于新 run 的 session-busy 判定。busy 只拒绝新接纳，应用可以持久排队后重试。secret、当前连接 key 或重试时间不作为逻辑请求摘要。

agent/session/run/timer 逐项校验 tenant 归属。subject_ref/scope_id 是可信调用方绑定并由服务端校验的 opaque 引用，metadata 不自行授予访问权。

应用部署使用 `API_AUTH_MODE=on` 和租户 Bearer key；bootstrap admin key 仅用于初始化组织/签发租户 key，以及平台 operator 的动态 target 注册/撤销。租户 key 不能改回调接收方。Bots 仍须按自己的配置与来源验证具体 Bot/scope。匿名开发模式不作为隔离验收证据。run 的 audit/calls 查询采用与结果查询相同的租户归属校验。

创建 agent 的 config 选择 `application_profile: true`，并指定 `application_bridge_ref`、固定 `application_tools`（`model_alias/tool_ref/description/input_schema`）。模型别名使用 `[a-zA-Z0-9_-]{1,64}`，每个别名和内部引用唯一，schema 根类型为 object、引用限本地。`max_steps/max_output_tokens/max_duration_ms` 的缺省上限分别为 16/4096/300000；负数和溢出值拒绝。

创建 session 时提交 `subject_ref/scope_id` 并冻结，应用 profile 不接收 participants。提交 run 时提供 `input` 和稳定 `origin_command_id`；`topic/trigger` 可选，均参与请求哈希。deadline 在首次接纳时绑定，重试不延长。run 的 input/topic 同样从持久命令核对，错误投递的 workflow body 不能借用原命令的权限。

首次 agent/session 创建返回 201，同请求重试返回 200 和原 ID；初始化未确认时保留 created 状态，重试同键恢复初始化，不覆盖后续状态。run 首次接纳返回 202 和 Location，重试返回 200 和已有状态。`session_busy` 与 `idempotency_conflict` 分别使用 409 + `error_code`，调用方不可用新 key 绕过未知结果或冲突。`queue:true` 不属于本期协议，排队归应用。

所有 HTTP 错误（含认证中间件）返回稳定信封 `{code,error_code,error,category,retryable}`；每个响应带 `X-Chronotope-Application-Contract: 1.0.0`。`error` 仅诊断，分支只用 `error_code`/`category`/`retryable`。完整码表见 [application-contract.v1.json](contracts/application-contract.v1.json)。

run 查询返回 `run_id/session_id/status/final/error/usage/bound`，终态还包含 steps。未终态结果可为 null；终态和结果同事务可见，同终态同结果重放成功、不同结果冲突。当前应用 profile 只开放 session 读、事件与 run 提交；旧 session actions/MCP/skills/schedules 等入口关闭。Bot 启停和发送 claim 由应用控制，不把旧 pause 接口当作 Bot 治理开关。机器可读字段见 [OpenAPI](contracts/session-api.openapi.yaml)。

## 2. 应用工具 Bridge

应用配置一份固定工具表：model alias、内部 tool ref、description、input schema；映射一一对应，只有表内工具能调用。工具服务 URL/认证来自受信服务配置，不能通过模型 arguments 传入。

示意调用信封：

```text
ApplicationToolCall {
  context: {
    tenant_id, subject_ref, scope_id, origin_command_id,
    run_id, operation_id, tool_call_id
  },
  tool_ref,
  arguments
}
```

context 来自已绑定 run，不来自模型。应用验证服务认证、subject/scope 与参数；Bots 将 opaque subject_ref 解释为 BotID。实际 source/reply target 等应用上下文由 origin 引用查询，不让模型构造目标或权限。

一轮模型调用产生的全部 tools 由 worker 处理，success/error 都回到原 call。内核保存本次调用的请求和结果，重放不重新产生新逻辑 operation。应用写操作应把 operation ID/request hash/原返回值与对象修改同事务保存，防止成功响应丢失后重做；这不是 MCP 协议自动提供的保证。

模型结果已知但计量缺失时保留结果，分别记录 usage_unknown/result_unknown。一次应用工具接纳 ACK 只证明这一跳，不等于应用已经向最终 provider 发出动作。

bridge target 可由静态 env 或动态注册提供；解析时按 ref 每次读取当前 target，校验 run bound tenant，读取 `token_env` 的服务凭据。bridge 路由字段（tenant/ref/URL）不可变，轮换 token 不改 digest；撤销/缺失时 tool call fail closed，不静默改投。工具失败记录 `tool.bridge` 日志和 `tool_bridge_*` 指标，含 run/tenant/operation/tool 关联，不含 arguments/result 正文。

本期只实现这一条 HTTP 调用通道；MCP 订阅/Tasks、A2A、动态工具发现、SDK 状态接管不在合同内。应用自行选择知识表和业务台账，不要求先接通通用 Record API。

## 3. Timer 回调

timer 只保存通用标识/时间和 opaque action ref。使用 Restate Sleep 耐久等待，回调目标来自应用注册配置（静态 env 或动态 target，ref+digest 冻结）；不解释提醒、工单、频道或任务完成规则。

timer 的幂等身份为 `(tenant_id,timer_id,revision)`，due_at 统一为 UTC 微秒精度。同键不同 subject/scope/due/action 冲突；改期用新 revision。Sleep 尚未创建时按绝对 due_at 计算当下剩余时间，已创建的 Sleep 保留 journal 中的原唤醒时刻；过期时仍调用稳定命名的 Sleep(0)，保持重放结构一致。

到点信封示意：

```text
TimerFire {
  tenant_id, timer_id, revision, fire_id, opaque_action_ref
}
```

fire_id 在重投时稳定，payload 不随重试改写。应用在自身事务持久接纳 fire 后才 ACK；只有该 ACK 才结束唤醒交付这一跳。响应丢失可重投，应用须幂等处理；应用暂停也可接纳并延后处理，不能要求 timer 重新计时才保留待办。

旧 timer 是否有效，由应用在实际工作 claim 前检查自己的 revision/status。底层 Sleep 取消是资源优化，正确性不依赖它；定时触发不自动执行模型，也不自动创建新的聊天 session。

timer 行本身保存提交责任，后台仅等待 Restate `/send` 耐久接纳；失败后仍可查询与重投。回调网络/非 2xx 为未确认，记录 `last_error_code` 并重投原 fire；目标 ref/绑定/URL 摘要变化或撤销时 blocked（`timer_target_changed` / `timer_target_unavailable`），拒绝悄悄切换接收方。已 acknowledged 的状态不被迟到提交/错误覆盖。动态 target 的 timer 地址变更会改变 digest，旧 timer 在发送前即 blocked；token_env 轮换不改变 digest。

## 4. 单一权威与验收

Chronotope 对 runtime state、模型调用、工具 RPC 和 timer/fire 的技术事实负责。应用对其业务修改、最终 sender、provider receipt/unknown 和原生验收负责，不能共写另一侧 DAO。

模型历史由 Chronotope 维护；应用保存 handle/来源/所需结果，不同时给 SDK/服务端另一套 history 做重复 replay。应用 profile 可关闭宽泛 tenant knowledge/自动 consolidation，改用自己的受限知识工具。

同版本进程恢复保留 PG/Restate；开发 `down -v` 是新测试代次，允许放弃旧 schema/API，但不能据此声称已验证恢复或撤销外部效果。双方按各自故障 fixture 再联调，最终产品门槛见 Bots 主方案。

## 5. 部署配置与当前验证入口

API 和 worker 使用相同的受信配置：`APPLICATION_BRIDGES_JSON` 为 `{ref,tenant_id,url,token_env}` 数组；`APPLICATION_TIMER_TARGETS_JSON` 为 `{ref,tenant_id,subject_ref,scope_id,callback_url,token_env}` 数组。`token_env` 指向部署环境中非空服务凭据，JSON 不接受内联 token。Compose 默认转发 `APPLICATION_SERVICE_TOKEN`；其它变量名须由部署显式注入。

动态 target（migration 040）是静态配置的运行时 overlay：operator 经 `POST /orgs/{org}/application-targets` 注册，API/worker 每次使用时解析，无需重启；静态 ref 不可被动态遮蔽。API/worker 必须都能解析同一个 `token_env`，否则解析 fail closed。target 变更写 `application_target_audit`，日志/指标不含 token。完整设计见[动态 target 注册与 fencing](动态-target-注册与-fencing.md)。

bridge 只能由配置所属租户使用，回调不跟随重定向。URL 与服务 token 均不进入模型请求、agent 配置或 run 快照；timer 只保存目标引用及不含凭据的摘要。API/worker 启动时拒绝无效或歧义配置。

`python3 test/e2e/application-runtime.py --mode fake` 用测试接收器的 SQLite 持久账本验证主路径，fake 模型经真实 Python provider HTTP 协议返回全部调用；`--mode real --model <model>` 使用实际 LiteLLM 上游并独立记录。该 fixture 不实现 Bots 产品或 Slack 发送，结果不能替代 Bots 的 G1 验收。

不依赖真实 Slack/Bots 的契约门禁见 `test/contract`、`test/contract/fakeapp` 和
`internal/api/application_contract_test.go`；运行方式见
[应用契约 v1.0.0](contracts/application-contract.md) §4。
