# 应用接入契约：有限运行、工具与通用 Timer

> 2026-10-19。**MVP 目标合同，待实施**；新增 API 及字段不是当前已交付清单。源码改动与验收见[期 8](./期8-细化落地方案.md)。本期允许破坏性变更，不建设旧版兼容路径。
> Chronotope 提供执行机制。应用拥有自身对象/策略/队列和最终验收；Bots 的消费行为以[Bots MVP](../../bots/docs/MVP设计.md)为准。

## 1. 控制接口

| 能力 | 目标接口及结果 |
|---|---|
| 创建不可变 agent 配置 | `POST /orgs/{org}/agents`；带稳定 Idempotency-Key，返回 agent ID/config digest |
| 创建技术 session | `POST /agents/{agent}/sessions`；带稳定 Idempotency-Key，返回 session ID |
| 接纳有限 run | `POST /sessions/{session}/runs`；同事务保存 command/outbox，返回 `202 + run_id` |
| 查询结果 | `GET /runs/{run}`；status、final/error、usage 和 bound 配置引用；终态与结果同一提交后可见 |
| 接纳单次 timer | `POST /timers`；稳定 timer_id/revision/due_at/opaque_action_ref，返回 `202 + timer_handle` |

幂等键均在受权 tenant/资源命名空间内解释；同键同规范请求返回原 ID/result，异请求拒绝。查询幂等结果先于新 run 的 session-busy 判定。busy 只拒绝新接纳，应用可以持久排队后重试。secret、当前连接 key 或重试时间不作为逻辑请求摘要。

agent/session/run/timer 逐项校验 tenant 归属。subject_ref/scope_id 是可信调用方绑定并由服务端校验的 opaque 引用，metadata 不自行授予访问权。

## 2. 应用工具 Bridge

应用配置一份固定工具表：model alias、内部 tool ref、description、input schema；映射一一对应，只有表内工具能调用。工具服务 URL/认证来自受信服务配置，不能通过模型 arguments 传入。

示意调用信封：

```text
ApplicationToolCall {
  context: {
    tenant_id, subject_ref, scope_id, origin_command_id,
    run_id, operation_id, tool_call_id
  },
  tool_ref,
  arguments
}
```

context 来自已绑定 run，不来自模型。应用验证服务认证、subject/scope 与参数；Bots 将 opaque subject_ref 解释为 BotID。实际 source/reply target 等应用上下文由 origin 引用查询，不让模型构造目标或权限。

一轮模型调用产生的全部 tools 由 worker 处理，success/error 都回到原 call。内核保存本次调用的请求和结果，重放不重新产生新逻辑 operation。应用写操作应把 operation ID/request hash/原返回值与对象修改同事务保存，防止成功响应丢失后重做；这不是 MCP 协议自动提供的保证。

模型结果已知但计量缺失时保留结果，分别记录 usage_unknown/result_unknown。一次应用工具接纳 ACK 只证明这一跳，不等于应用已经向最终 provider 发出动作。

本期只实现这一条 HTTP 调用通道；MCP 订阅/Tasks、A2A、动态工具发现、SDK 状态接管不在合同内。应用自行选择知识表和业务台账，不要求先接通通用 Record API。

## 3. Timer 回调

timer 只保存通用标识/时间和 opaque action ref。使用 Restate Sleep 耐久等待，固定回调目标来自应用注册配置；不解释提醒、工单、频道或任务完成规则。

到点信封示意：

```text
TimerFire {
  tenant_id, timer_id, revision, fire_id, opaque_action_ref
}
```

fire_id 在重投时稳定，payload 不随重试改写。应用在自身事务持久接纳 fire 后才 ACK；只有该 ACK 才结束唤醒交付这一跳。响应丢失可重投，应用须幂等处理；应用暂停也可接纳并延后处理，不能要求 timer 重新计时才保留待办。

旧 timer 是否有效，由应用在实际工作 claim 前检查自己的 revision/status。底层 Sleep 取消是资源优化，正确性不依赖它；定时触发不自动执行模型，也不自动创建新的聊天 session。

## 4. 单一权威与验收

Chronotope 对 runtime state、模型调用、工具 RPC 和 timer/fire 的技术事实负责。应用对其业务修改、最终 sender、provider receipt/unknown 和原生验收负责，不能共写另一侧 DAO。

模型历史由 Chronotope 维护；应用保存 handle/来源/所需结果，不同时给 SDK/服务端另一套 history 做重复 replay。应用 profile 可关闭宽泛 tenant knowledge/自动 consolidation，改用自己的受限知识工具。

同版本进程恢复保留 PG/Restate；开发 `down -v` 是新测试代次，允许放弃旧 schema/API，但不能据此声称已验证恢复或撤销外部效果。双方按各自故障 fixture 再联调，最终产品门槛见 Bots 主方案。
