## 1. P0 — 阻塞项

### P0-1 background 子代理建行但不发动

**位置**：`internal/restate/subagent.go:83-88`

```go
if ownership == "background" {
    b, _ := json.Marshal(map[string]any{"status": "spawned(background)", "child_run_id": outcome.RunID})
    return string(b), 0, nil   // ← 无 dispatch
}
```

**失败场景**：模型调 `spawn_subagent{ownership:"background"}` → 闭包内已 `CreateRunWithCommand`（`runs.status='queued'`）→ 直接返回 → **没有任何地方调用 `restate.Workflow[RunWorkflowName]`**。全仓发动点只有三处：`subagent.go:93`（foreground）、`group.go:78`、`scheduler.go:108`。

后果链：
1. 子 run 永久 `queued`；模型已收到 `spawned(background)`，据此认为任务已启动
2. `AdmissionRecovery` 5 分钟后捞它重投（`api/recovery.go:44-64`），此时 input 已落库（十期 #14 修复），**所以能被救活**
3. 但在那之前，父 run 可能已结束、`maxSteps` 耗尽、或管理方已判定任务丢失

即：**不是永久死代码，是「5 分钟延迟 + 依赖 recovery 兜底」**，且对模型撒谎。

**方案（已定案：A — 用 SDK 原生 one-way 调用）**：

SDK 1.1.0 **原生支持** fire-and-forget，无需自建队列。证据：

| 证据 | 位置 |
|---|---|
| `SendClient[I]` 接口，`Send(input, opts...) Invocation` —— 注释即「one-way call which is executed in the background」 | `sdk-go@v1.1.0/rpc.go:63-68` |
| `Invocation` 只有 `GetInvocationId() string`，**无 `Response()`** | `internal/restatecontext/call.go:21-23` |
| `Send` 走 `SysSend`（`call.go:185`），与 `RequestFuture` 的 `SysCall` 是状态机里两个不同函数 | `internal/statemachine/wasm.go:216-217` |
| `SysSend` 返回 `invocationIdHandle`，经 `newAsyncResult` 缓存 —— 重放回放同一 invocation id，不重复发动 | `call.go:190-192` |
| `options.SendOption` 含 `WithIdempotencyKey` | `rpc.go:205` |

关键性质三条：
1. **真 detached**：立刻返回，父 run 不挂起、不等结果
2. **journaled 且幂等**：与现有 journal 纪律同构，重放安全
3. **按 key 去重**：`runID` 即 workflow key，Restate 天然去重

修复（`subagent.go:85`）：

```go
if ownership == "background" {
    restate.WorkflowSend[RunInput](ctx, RunWorkflowName, outcome.RunID, "run").
        Send(RunInput{SessionID: outcome.SessionID, Input: input})
    b, _ := json.Marshal(map[string]any{"status": "spawned(background)", "child_run_id": outcome.RunID})
    return string(b), 0, nil
}
```

⚠️ **两条落地注意**：

1. **依赖 P0-3 先修**。background 一旦能跑长任务，「会话睡久 → 沙箱被回收 → 409 lease expired」就从边缘场景变主路径。顺序上先做 P0-3。
2. **`Send` 不传播取消**。父 run 被取消时子 run 照跑——这是「取消不向子传播」缺口在组合层的又一实例。落地时至少留决策记录（接受 / 加显式 cancel 传播），别静默。

**回归测试**：`internal/restate/subagent_test.go` — background 分支返回后，断言子 run 进入 `running`；父 run 不阻塞（返回时间不随子 run 时长增长）。

### P0-2 run 取消的用量永不进账本

**位置**：`internal/core/sessionapi/sessionapi.go:38,40` + `internal/api/usage.go:104,161`

```go

RunCancelled RunStatus = "cancelled"   // 另一套拼写
```

`run_workflow.go:272,425` 发的是 `event.RunCanceled`；`usage.go:104,161` 的终态判定只认 `event.RunCancelled`。

**失败场景**：任何被取消的 run，其 token/compute 用量**全量丢失**，不进 `usage` 表。对多租户平台这是**计费漏账**，不是显示问题。且取消的 run 往往是最贵的（跑到一半被砍）。

**方案（已定案：无生产环境，直接删——不留兼容层）**：

2. `usage.go:104,161` 两处 `case` 的 `event.RunCancelled` 改为 `event.RunCanceled`。
3. 从 `event.go:71` 的 `Type.Valid()` 分支里移除 `RunCancelled`（只增不改纪律下这是删除——但因无生产数据，直接删不引入过渡期）。
4. 同步更新 `契约规范.md §5` 事件类型全集表（删除 `run.cancelled` 行），保持文档与代码一致。

⚠️ **重建**：既有开发库若含 `run.cancelled` 类型的历史事件行，`Type.Valid()` 将拒绝它们。与 P1-4 同批做全库重建。

**回归测试**：`internal/api/usage_test.go` — 造一个 `run.canceled` 事件，断言用量被计入。

### P0-3 沙箱租约过期不在恢复哨兵内

**位置**：`internal/restate/dispatch.go:37-47`（`sandboxGone`）vs `internal/execproto/server.go:316-323`

executor 在 TTL 过期且无有效租约时返回 **409 `sandbox lease expired`**（`server.go:322`），但 `sandboxGone` 只认：
- `errors.Is(err, execproto.ErrSandboxNotFound)`
- 文本 `"sandbox not found"` / `"sandbox destroyed"`

**409 lease expired 不在哨兵内 → 被当普通错误 → `execWithSandboxRecovery` 不触发重建 → terminal 失败。**

**失败场景**：这正是「一周前会话今天还能继续」那条产品主张。会话休眠超过 TTL → worker 执行 → executor 判租约过期 → 409 → 无重建 → run 失败。**恢复链在它最重要的场景里断了。**

**方案**：在 `sandboxGone` 里加 lease-expired 判定。但**不能只加文本匹配**——409 也用于 in-flight 与 holder 不匹配（`server.go:325`），误判会扩大重建。需要**区分**：

```go
// leaseExpired 判租约过期（与 in-flight/holder 不匹配区分——三者同为 409）
func leaseExpired(err error) bool {
    return err != nil && strings.Contains(err.Error(), "sandbox lease expired")
}
```

然后在 `dispatch.go:122` 的判定里：`if sandboxGone(err) || leaseExpired(err)` → 标 404 哨兵。

⚠️ **同时要处理**：lease expired 意味着沙箱**仍在运行**（只是租约失效），重建前必须确认旧沙箱不被误留为孤儿。当前 `ClearSandbox`（`dispatch.go:56`）只清绑定，不销毁旧沙箱。**建议在重建路径上加一次 best-effort `Snapshot` 或 `Destroy`**，否则每次 lease 过期都留一个孤儿容器（`GC` 要等 TTL 才收）。

**回归测试**：`internal/restate/dispatch_test.go` — fake executor 返回 409 lease expired，断言「清绑定 + 重建 + 重试一次」三步都发生。

## 2. P1 — 加固项

### P1-1 `ResolveWait` 零行匹配返回 nil（承诺静默失真）

**位置**：`internal/store/session_waits.go:36-42`

```go
if _, err := s.Pool.Exec(ctx, q, ...); err != nil {   // ← tag 被丢弃
    return fmt.Errorf(...)
}
return nil
```

**失败场景**：handle 不匹配 / 已 resolved / session 不符 → 0 行 → 返回 `nil` → 调用方认为已解决。**「解决成功」和「静默失败」在类型上不可区分。**

两个调用点都丢弃了返回值（`dispatch.go:283,287` 的 `_ =`），加上 `recovery.go:85-88` 的 TTL 超时路径——**resolve 没生效时系统认为承诺已了结，而 run 仍挂着**。

**方案**：返回 `RowsAffected`，调用方按需判定：
```go
func (s *Store) ResolveWait(...) (bool, error) {
    tag, err := s.Pool.Exec(ctx, q, ...)
    if err != nil { return false, fmt.Errorf(...) }
    return tag.RowsAffected() > 0, nil
}
```
调用点：`awaitApproval` 里 0 行需记事件（可观测）；`recovery` 的 TTL 路径 0 行应告警（说明 handle 已失配）。

这同时也是「承诺」机制的地基——commitment 状态机依赖「兑现是否真的落库」可判定。

**回归测试**：`internal/store/store_test.go` — 重复 resolve 断言第二次返回 `false`。

### P1-2 `RegisterWait` 的 upsert 会把已解决的重置为未解决

**位置**：`internal/store/session_waits.go:22-33`

```sql
ON CONFLICT (session_id, kind, handle) DO UPDATE
SET ..., registered_at = now(), resolved_at = NULL   -- ← 复活
```

对「同一 handle 的新一轮等待」这是对的；但 `awaitApproval` 每次挂起都用新 awakeable id，**handle 不复用**，所以这条 upsert 在当前用法下**只会在重放时复活一个已解决的 wait**。

**失败场景**：run 重放 → `RegisterWait` 同 handle 重放 → 把一个已 resolved 的 wait 打回 active → `ActiveWaits` 查询（`scheduler.go` 的 DECIDE 依据）看到幽灵等待 → 该派发时不派发。

**方案**：拆成语义明确的两个方法：
- `RegisterWait` — 纯 INSERT，冲突即 no-op（保持已解决状态）
- `RenewWait` — 显式复活（给真正需要「同 handle 新一轮」的调用方）

当前 `awaitApproval` 与 `scheduler` 都应改用具 no-op 语义的 INSERT。

**回归测试**：`internal/store/store_test.go` — register → resolve → register 同 handle，断言仍是 resolved。

### P1-3 `UpdateRunStatus` 无状态护栏（可覆盖终态）

**位置**：`internal/store/repos.go:219-229`

```sql
UPDATE runs SET status = $2, ... WHERE id = $1   -- ← 无状态条件
```

对比 `FinalizeRun`（`outbox.go`）有 `AND status NOT IN ('completed','failed','cancelled')` 护栏。

**失败场景**：`run_workflow.go:263` 的 paused 分支写 `RunFailed`，之后若同一 run 的另一条路径（重放、recovery 补交、api 的同步确认 `handlers.go:240`）再写一次 `RunCompleted` → **终态被覆盖**。`FinalizeRun` 有护栏挡住了主路径，但 `UpdateRunStatus` 是旁路。

**方案**：加终态护栏（幂等：已是终态则 no-op）：
```sql
UPDATE runs SET status = $2, ...
WHERE id = $1
  AND (status NOT IN ('completed','failed','canceled','cancelled') OR status = $2)
```
保留「同状态重写」为幂等成功，拒绝「终态→另一终态」。

**回归测试**：`internal/store/store_test.go` — completed → failed 断言被拒。

### P1-4 哈希链只写不验，且不含 seq/session_id

**位置**：`internal/store/events.go:17`（`sha256HexEvent`）、`:46-51`（写入）

全仓**无任何验证函数**（`grep -i verify` 在 `internal/api/` 零命中）。审计导出（`ListEventsWithChain`，`events.go:157`）把链交给读者，平台自己不做篡改检测。

且 `sha256(prev_hash || type || payload)` 的输入**不含 `seq` 与 `session_id`** → 删除中间一行再重排**不会被发现**。

**方案（已定案：无生产环境，直接改公式，不做向前兼容）**：

1. **补输入**：`eventHash = sha256(prevHash || sessionID || seq || type || payload)`。历史行按旧公式算的哈希**直接作废**——开发环境重建，无需 `chain_version` 兼容层。
2. **加验证**：`VerifyChain(ctx, sessionID) (brokenAtSeq int64, err error)` — 顺序读，逐行重算比对 `prev_hash` 与 `event_hash`。
3. **接入导出**：`/sessions/:id/export` 输出加 `chain_verified: bool` + `broken_at_seq`，让审计消费者拿到平台自己的结论而非裸数据。

⚠️ **重建方式**：改公式后，既有开发库的 `prev_hash`/`event_hash` 全部失效。提供一个一次性重建函数（按 seq 顺序重算全表哈希）或直接 drop 开发库重跑 `Migrate()`（`store.go:41`）。**不要留下半新半旧的链**——`VerifyChain` 会在中间断点误报。

**回归测试**：`internal/store/store_test.go` — 手工 UPDATE 一行 payload，断言 `VerifyChain` 报出该 seq。

### P1-5 补偿动作未 journaled，重放可能不落地

**位置**：`internal/restate/run_workflow.go:124,263,275,425,529`

`UpdateRunStatus` 有 6 处调用，**全部是裸调用，没有包在 `restate.Run` 里**。对比 `emit.Emit` → `AppendEvent`（dedupe 幂等）与 `releaseLease`（`run_workflow.go:181`，**正确包在 `restate.Run` 内**）。

**失败场景**：worker 在「效果已发生、终态未写」窗口崩溃 → 重放时这些写**依赖 SDK 的判断**是否重试。而 `emit`/`releaseLease` 是显式 journaled 的，两者纪律不一致。原则上「不可重放的副作用」必须在 journal 边界内。

实际后果没有 P0 严重（`UpdateRunStatus` 是幂等的、recovery 会扫孤儿补交），但它**破坏了「所有副作用都在 journal 边界内」这条可验证的纪律**，而这正是这个内核的立身之本。

**方案**：统一包进 `restate.Run`：
```go
_, _ = restate.Run(ctx, func(rc restate.RunContext) (struct{}, error) {
    return struct{}{}, deps.Store.UpdateRunStatus(rc, runID, sessionapi.RunFailed)
}, restate.WithName(StepName("run-status", step, "failed")))
```
注意 `StepName` 需保证同一逻辑位置名字稳定（重放回放同一条 journal）。

**同时**：`dispatch.go:56` 的 `ClearSandbox` 同样是裸对象调用，应一并处理。

**回归测试**：`internal/restate/run_workflow_test.go` — 断言终态写在 journal 里出现（golden 测试）。

### P1-6 会话级 dedupe 键有损

**位置**：`internal/restate/emit.go:34-40`

`runID == ""` 时键为 `sessionID:kind[:tool]`。受影响的三处：

| 位置 | 键 | 后果 |
|---|---|---|
| `run_workflow.go:302` | `sessionID:event.truncated:tools` | 同会话第二次 MCP 降级不可见 |
| `webhook.go:117` | `sessionID:audit.approval:<runID>` | 同 run 内第二次审批不留痕 |
| `session_object` 级事件 | `sessionID:<kind>` | 会话内重复动作被吞 |

**方案**：给 `Emit` 加可选区分维度。最小改动是让调用方把区分信息编进 `kind`（如 `"truncated:mcp:"+server`），但这依赖调用方自觉。更好的做法是加一个显式 `dedupeSuffix string` 参数——**但会改动所有调用点**。

**推荐**：先只修 worst case（`event.truncated` 加 server 维度、`audit.approval` 的键改为含 step），因为这两处是真的丢审计/丢可观测性。全量重构留到有明确需求时。

**回归测试**：`internal/restate/mcp_test.go` — 同会话两次 MCP 降级，断言两条事件都在。

## 3. P2 — 清理项

### P2-1 `deferFree` 是重构残留

**位置**：`internal/restate/dispatch.go:259,288-289`

```go
deferFree := true
...
deferFree = false
_ = deferFree     // ← 三条语句，零作用
```

是「去掉 defer」那次重构的遗留。直接删。

### P2-2 `stepSpan.End()` 的 defer 在循环内

**位置**：`internal/restate/run_workflow.go:207`

循环内 `defer` 累积，span 生命周期被拉到函数返回（最长 16 步）。正确做法是立即 `End` 或在循环体内显式管理。不影响正确性，但污染 trace（`OTEL_EXPORTER=stdout` 时可见）。

### P2-3 `run_completed` 的字段语义混淆

**位置**：`internal/restate/run_workflow.go:550`

```go
payload := map[string]any{
    "final": res.Final, "steps": step + 1, "truncated": res.Truncated,
    "tokens_in": accTokens, "compute_seconds": accCompute,   // ← accTokens 是 in+out 之和
}
```

`accTokens = sum(TokensIn + TokensOut)`，却写进 `tokens_in` 字段。而 `llm.call` 事件的 `usage.tokens_in` 是纯输入。聚合器（`usage.go`）若同时消费两处，**会双计或串轴**。

**方案**：改名 `tokens_total`，或在聚合器里明确只认 `llm.call` 的 usage、忽略 `run_completed` 的该字段。需先确认 `usage.go` 当前读哪个——若只读 `llm.call`，则此字段是纯误导，改名即可。

### P2-4 沙箱销毁路径未在重建时清理

见 P0-3 的注意事项。lease expired 触发重建时，旧沙箱既没 destroy 也没 snapshot，成为孤儿等 GC。

**全库重建窗口**：第 1 步（删除 `run.cancelled` 类型）与第 9 步（哈希公式变更）都会让既有开发库的历史行失效。建议这两步**同批完成**，然后 drop 开发库重跑 `Migrate()`，避免半新半旧的链与新类型混存。

## 5. 前置决策（已定案）

### D-1 background ownership：确认采用 `Send`（A 方案）

**结论：SDK 1.1.0 原生支持 fire-and-forget，采用 A，不自建队列。**

证据链见 P0-1。要点：
- `SendClient.Send` 返回 `Invocation`（仅 `GetInvocationId()`，**无 `Response()`**）——真 detached
- 底层 `SysSend` 与 `RequestFuture` 的 `SysCall` 是状态机里两个不同函数
- journaled 且经 `newAsyncResult` 缓存——重放回放同一 invocation id，与现有 journal 纪律同构

**遗留决策（落地时补决策记录，不阻塞）**：`Send` 不传播取消。父 run 取消时子 run 照跑。是否加显式 cancel 传播，待 background 有真实使用场景后再定。

### D-2 哈希链公式变更：直接改，不做兼容

**结论：无生产环境，开发库可重建，因此不做 `chain_version`、不做双公式验证。**

- `eventHash` 输入改为 `sha256(prevHash || sessionID || seq || type || payload)`
- 既有开发库的历史哈希**直接作废**，drop 重跑 `Migrate()`
- 不提供按时间戳/版本分支选公式的兼容路径——那是给有生产数据的系统准备的

⚠️ 对应地，P0-2 的 `run.cancelled` 类型删除也走**直接删**路径，不保留 deprecated 常量。这两处是同一种决策（无兼容期），应同批重建。
