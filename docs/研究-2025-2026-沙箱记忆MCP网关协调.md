# 时空可组合持久化运行时：2025–2026 生产方案研究摘要

## 1. 沙箱矩阵与生产形态

**核心设计要点**
- **E2B**（[docs](https://e2b.dev/docs)、[GitHub](https://github.com/e2b-dev/e2b)）：基于 Firecracker 微虚拟机，冷启动约 150ms（Firecracker snapshot/restore 机制）。支持 **pause/resume**（RAM+磁盘整机快照挂起，请求到达自动恢复）、**snapshot/fork**（含内存与进程的完整克隆，可"时间旅行"）、filesystem-only snapshots、模板构建器、OTel 遥测。**BYOC**（Bring Your Own Cloud）：编排控制面在 E2B，沙箱基础设施跑在客户云账号（如 [Devin Outposts](https://e2b.dev/resources/devin-outposts) 即用 E2B 作为执行层）。
- **隔离取舍**（[Northflank: Firecracker vs gVisor](https://northflank.com/blog/firecracker-vs-gvisor)、[vs Kata](https://northflank.com/blog/kata-containers-vs-firecracker-vs-gvisor)）：runc 容器共享内核，最快但隔离最弱，仅靠 seccomp/AppArmor 兜底；gVisor 用户态内核（Sentry）拦截 syscall，轻量、共享宿主内核；Kata 是标准 OCI 接口的真 VM，最重；Firecracker 微虚拟机硬件级隔离 + 毫秒级快照恢复，是"不可信代码 + 高密度 + 快恢复"的当前最优解。
- **Wasm 沙箱**（[agentpatterns: In-Process WebAssembly Sandboxes](https://raw.githubusercontent.com/agentpatterns-ai/website/refs/heads/main/security/wasm-sandbox-agent-code-execution.md)）：Wasmtime + WASI，进程内启动、near-native、capability 授权，适合短时确定性计算，无完整 Linux 文件系统语义；[microsandbox](https://microsandbox.dev/compare/e2b) 提供云端/本地运行时与文件同步快照。
- **云厂商 Agent Sandbox**：阿里云函数计算云沙箱，已发布 [Snapshot 商业化计费公告](https://help.aliyun.com/zh/functioncompute/cloud-sandbox-snapshot-commercial-billing-announcement)（快照按存储与恢复计费）；Cloudflare Sandboxes 面向 coding agent，[workspace save/restore](https://developers.cloudflare.com/sandbox/files/save-and-restore-a-workspace/)。
- **持久化生产做法**：① 独立卷挂载（R2/S3/volume，跨沙箱存活）；② 备份归档 + 恢复——Cloudflare 生产实现为 squashfs 只读 lower 层 + FUSE **overlayfs** 可写 upper 层，原归档不可变，注意 EXDEV 跨设备 rename 坑（[backup-restore](https://developers.cloudflare.com/sandbox/sdk/concepts/backup-restore/)）；③ 镜像 + 卷（进程重建、数据留存）；④ 微虚拟机快照（进程态+数据态整体冻结，最接近"时间旅行"，但存储与 GC 成本高）。

**启示**：分层持久化 = 不可变镜像模板 + 持久卷（workspace/知识）+ 会话级快照/overlay 检查点。快照必须纳入计费并设保留期/版本 GC；"时空组合"的直接载体是快照/分支（fork）与 overlay。

## 2. Agent 记忆架构前沿

**核心设计要点**
- **Letta（MemGPT）**（[memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks/)、[context hierarchy](https://docs.letta.com/v1-sdk/memory/context-hierarchy/)）：记忆显式化为**命名的 memory blocks**（persona/human 等 key-value），agent 通过 self-edit 工具自主改写核心记忆——"记忆即状态，而非仅提示词拼接"。三层上下文层级：core memory（常驻上下文）→ recall/archival memory（外部向量库按需检索）→ recursive summarization 防遗忘。**Shared memory blocks** 支持跨 agent/跨会话共享；**consolidation** 以后台 heartbeat 作业在空闲时执行（休眠期整理记忆）。
- **分层共识**：工作记忆（会话内 in-context）/ 情景记忆（近期事件 rollup）/ 语义记忆（事实）/ 程序记忆（技能），见 [AutomatosAI 五层架构](https://github.com/AutomatosAI/automatos-ai/blob/ca5fea09a60321a6f06d58c46486f2147d2e76a7/docs/memory-system/five-layer-memory-architecture.md)。
- **组合策略**：RAG（检索）+ 摘要（巩固）+ 自编辑（精炼）混合；巩固时机 = 会话边界、token 阈值触发、空闲 heartbeat；唤醒时先重放记忆再推理。
- **向量库**：[pgvector](https://github.com/pgvector/pgvector) 成为生产默认——与业务库同库、行级安全天然多租户、HNSW/IVFFlat、与 JSON 元数据共查。租户隔离靠 agent 维度 block + 行级安全 + 每租户命名空间/collection。

**启示**：持久化运行时必须把记忆当作**一等持久状态**：内存块（编辑型）+ 归档库（检索型）双层；跨会话/跨 agent 共享块 + 租户隔离；巩固作为调度器内的后台任务，与沙箱空闲窗口对齐。

## 3. MCP 生产化

**核心设计要点**
- **规范演进**（[2025-11-25 spec](https://modelcontextprotocol.io/specification/2025-11-25)）：2025-06-18 起 **Streamable HTTP** 取代 HTTP+SSE——单端点 POST/GET、可选 SSE、断线重连（Last-Event-ID）、[会话管理与可恢复性/重投递](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)；安全加固：服务端必须校验 Origin 防 DNS rebinding。[授权规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)：OAuth 2.1 + RFC 8707 resource indicators + PKCE + 动态客户端注册 + step-up 授权，支持工具级 scope。
- **stateless vs stateful**：stateless 服务器每请求独立，适合 API 包装；stateful 服务器持有资源（终端/浏览器/沙箱），须会话绑定 + 租户身份注入。Streamable HTTP 兼容两者（可无会话，也可 session ID）。
- **注册表/网关**：官方 [Registry](https://registry.modelcontextprotocol.io/)、[Docker MCP Enterprise Gateway](https://www.docker.com/products/mcp-enterprise-gateway/)、Cloudflare Remote MCP。企业模式 = 网关集中 OAuth/token exchange、工具白名单、工具级 RBAC、客户端注册审批（trust policy）、全量审计日志。
- **状态归属**：生产共识是 **MCP 服务器无状态化、状态归 runtime**——沙箱/工作区/记忆 ID 作为工具参数传入，MCP 只做执行与授权；网关做会话粘性路由与审计。

**启示**：MCP 是接入层而非状态层。runtime 内建"工具注册表 + 授权策略 + 审计事件"，把工具状态持久化到自身（沙箱、记忆、文件），避免有状态 MCP 服务器成为第二状态源。

## 4. 多租户 LLM 网关与计费

**核心设计要点**
- **LiteLLM**（[docs](https://docs.litellm.ai)）：开源网关事实标准，100+ 供应商统一 OpenAI 格式；**virtual keys → budget（max_budget + budget_duration）→ 硬熔断**；teams/organizations/end-users 三级配额；spend 追踪、Prometheus/Datadog、SSO、fallback/retries、RBAC。
- **云厂商托管网关**：Azure AI Foundry、AWS Bedrock + API Gateway、GCP Vertex AI Gateway、阿里云百炼、OpenAI 平台（org/project keys + spend limit）；商业网关 Portkey/gateway.ai（virtual keys + budgets + guardrails）。
- **计量模型**：token（input/output/cached）× 计算秒（阿里云沙箱按 vCPU·秒，E2B 按沙箱运行时间）× 存储/快照 × 工具调用——多维计量事件流。开源计量计费：[Lago](https://github.com/getlago/lago)（含 [Lago Agent SDK](https://docs.getlago.com/guide/ai-agents/agent-sdk)，直接给 agent 打点计量）、OpenMeter（Cloud Metering）。
- **预算熔断**：网关层（请求前检查 + 实时 spend）+ 调度层（任务中止）双层熔断；按 org/user 的 key 级隔离，预算与配额分开记账。

**启示**：runtime 计费 = 统一 usage 事件流（token + 计算秒 + 存储 + 快照）→ 计量引擎（Lago/OpenMeter）→ 配额/预算熔断。快照与卷存储的"时空占用"也应计费，与 LLM 网关共用一套账单。

## 5. 可组合多 Agent 协调拓扑

**核心设计要点**
- **水平黑板/群聊**：AutoGen GroupChat、CrewAI crew、LangGraph 共享状态——全员读写黑板，轮转/selector 调度；适合评审、辩论式协作，缺点是上下文膨胀与写冲突。
- **树形委派**：生产主流。[Anthropic 多 agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system) = orchestrator-worker，并行子任务 + 上下文隔离 + 结果合并；[Claude Code subagents/dynamic workflows](https://code.claude.com/docs/en/workflows)；OpenAI Agents SDK handoffs。子 agent 独立上下文、可并行、计费可归因。
- **A2A**（[spec](https://a2aproject.github.io/A2A/specification/)）：Google 主导，JSON-RPC 2.0 over HTTP，AgentCard 能力发现，Task 生命周期状态机（submitted→working→completed/failed/canceled），artifact 传递 + push notification；2025 年捐给 Linux 基金会，适合**跨组织**互操作，不适合低延迟内部编排；企业需求见 [IETF draft](https://www.ietf.org/archive/id/draft-zgsgl-dispatch-a2a-requirements-enterprise-00.html)。
- **Swarm**：OpenAI Swarm 演进为 Agents SDK——handoff + context variables，强调轻量交接而非深协调。
- **共享状态设计**：事件溯源日志 + 投影状态；任务对象持久化于 DB；写方需 ownership/租约防冲突。生产混合形态 = 顶层 planner 树形委派 + 同级 worker 黑板协作 + 跨组织 A2A。

**启示**："时空可组合"的落地语义：每个 agent/子任务拥有独立时空（沙箱快照 + 记忆块 + 工作区），协调层只传**引用**（sandbox id、memory block ref、artifact ref）与消息，状态零复制。拓扑选择：树形委派为骨架、黑板用于同级协作、A2A 预留给外部互操作。
